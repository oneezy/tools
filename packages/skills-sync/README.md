# @oneezy/skills-sync

One skills library. Every agent harness. Every machine, with nothing to set up on it.

```
npx @oneezy/skills-sync
```

Run it anywhere and it works out the rest. A machine command (`sync`, the default, `status`, `hook`, `branches`, `unlink`) keeps nothing of its own on the machine: no library clone, no `~/.skills-sync`, no answers file, nothing remembered between runs. Its settings come from the library's committed `skills-sync.json` at the release's commit on GitHub (see [The release's settings](#the-releases-settings)); what the machine has (its harnesses, on Windows its WSL distros) is detected on every run.

- **Every run** reads the latest release of `oneezy/skills` on GitHub (`--library owner/repo` for another) and writes the one skills block into each harness's global instructions file, `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`: the tool's pointer to the `/oneezy-agents` skill, which loads Justin's rules, plus the skill invocation table (see [The global block](#the-global-block)). Never a repository's `AGENTS.md` or `CLAUDE.md`; a block an older version left in one is reported for cleanup, not edited. `sync` clones nothing.
- **Claude Code** gets the library's skills from the account plugins claude.ai delivers (`<id>@synced`) and nothing else. For each one the release lists that claude lists as present and switched on, the run removes what hides or duplicates it: the same-named plugin an older skills-sync installed from the `oneezy-skills` marketplace (a CLI-installed plugin outranks the account one), then every loose link in `~/.claude/skills` named after one of its skills that points at a library checkout or clone, at `~/.skills-sync`, or at nothing (a dangling link counts as the tool's leftover, whatever it once pointed at). A link to somewhere else and a real skill folder are yours: named, never removed. A plugin the account does not deliver yet keeps whatever it has today and is one note: `<id>: not delivered by the claude.ai account yet; switch it on at claude.ai (Customize > Plugins), then sync again`; when `claude` lists no account plugin at all, one note points at the sign-in and `syncClaudeAiPlugins` instead. Plugins from other marketplaces and other account plugins are never touched; the marketplace registration goes once no plugin of the tool's remains. When `claude` is missing or cannot list its plugins, nothing is removed and one red line says so.
- **Codex** gets the library's plugins from the `oneezy-skills` marketplace added from GitHub (`codex plugin marketplace add oneezy/skills`); an older registration of that name from a local folder, the `~/.skills-sync` form, is removed and the GitHub one added in its place. Every plugin the release's `skills-sync.json` gives Codex (every one the release lists when its config names none; see [The release's settings](#the-releases-settings)) is installed (`codex plugin add <id>@oneezy-skills`). When one is behind the release, by version or by a skill it does not load, one `codex plugin marketplace upgrade oneezy-skills` brings the snapshot forward and reinstalls them; a plugin ahead of the latest release (the snapshot is `main`, which runs ahead after every push until the release job finishes) is a note, nothing to do. Each plugin is verified through `codex plugin list --json` and `codex debug prompt-input`: listed from `oneezy-skills`, enabled, not behind the release, loading every skill the release gives it. A user-only skill (the library gives every skill marked `disable-model-invocation: true` an `agents/openai.yaml` with `policy.allow_implicit_invocation: false`) is loaded by Codex and runs when you name it (`$name`, or the `$` and `/skills` pickers), but Codex keeps it out of the model's skill list, so the prompt input never shows it: it counts as loaded when the copy Codex runs (`~/.codex/plugins/cache/oneezy-skills/<id>/<version>/skills/<name>/`) holds its `SKILL.md` and that policy. Only then are that plugin's old copies removed from `~/.agents/skills` and the deprecated `~/.codex/skills`: a loose link into a library checkout or clone, into `~/.skills-sync`, or at nothing, and a real folder holding exactly the release's files for the skill. `.system` is Codex's own and is never listed or touched. Every other folder, and every link to somewhere else, is yours: one line each, adopt it into the library or delete it by hand. A plugin of the same name from another marketplace lists its skills a second time; it is never removed, the line says how to uninstall it. The ChatGPT account's own copies (`created-by-me-remote`, `workspace-*`) are the exception: they are the [ChatGPT destination](#chatgpt), so their line says they stay. When `codex` is missing or cannot list its plugins, nothing is installed or removed and one line says so. `--plan` runs only the listings.
- **Hermes** gets the library's plugins from GitHub. For every plugin the release's `skills-sync.json` gives Hermes (every one the release lists when its config names none; see [The release's settings](#the-releases-settings)), the run installs it through Hermes's own command at the release commit (`hermes plugins install oneezy/skills/dist/hermes/<id> --no-enable --ref <commit>`, from the Hermes rendering `build` writes beside each package once the library opts in; see [Plugins and catalogs](#plugins-and-catalogs)), enables it (`hermes plugins enable <id>`), and verifies it: `hermes plugins list` says enabled, the folder under `<hermes home>/plugins/<id>` carries the release's version, skill set and `NOTICE.md`, and every skill passes Hermes's portable rules. Only then do the loose links in `<hermes home>/skills` named after the plugin's skills come out, when they point at a library checkout or clone, at `~/.skills-sync`, or at nothing; a link to somewhere else and a real skill folder are named and left. A plugin behind the release is installed again at the new commit, the same plain call first, then once with `--force` (that is how a pinned install moves; `hermes plugins update` refuses one); see the scan below. A plugin hermes did not install for this library (no install row, another repository, a link, or one you disabled in `config.yaml`) is left alone with a red line, and so are its skills' links. A failed step is a red line and the links stay. Hermes scans every plugin it installs (`safe`, `caution` or `dangerous`), and with no terminal its question about a `caution` reads no, so a library plugin that ships scripts (diagram-design, pstack) would stop there: every install, fresh or a re-install, runs plain first, so the scan has its say, and when it says `caution` the run installs that same plugin again, once, with `--force` (the library's own `oneezy/skills/dist/hermes/<id>` at the release commit, both built by the tool and never read from the machine; a same-named plugin from anywhere else is never installed over). Hermes scans before it checks whether the plugin is already there, so a re-install of the tool's own install whose scan passes ends in Hermes's ``Plugin '<id>' already exists. Use force reinstall or run `hermes plugins update <id>`.``, and only then is it run again, once, with `--force` (no line: the scan was clean); a new `caution` on a re-install is answered and noted as on a fresh install, and a `dangerous` one leaves the plugin at the commit it had, with a red line, as does a plain call Hermes refuses for any other reason (a clone that fails, a link in the way): only a `caution` and "already exists" are retried. Hermes prints a verdict only when its scan stops an install (the report's `Scan: <id> (<identifier>/community)  Verdict: CAUTION` and `Blocked: Security scan blocked plugin install: Requires confirmation (caution verdict, <n> findings)`); a caution `--force` answers passes without a word, so the plain call is the one that tells. Every `hermes` command the tool runs gets `COLUMNS=1000`, so Rich prints each of those lines whole. Each install whose scan said `caution` gets one line, not a red one, that names it and what was overridden (`. note  Hermes: plugin pstack  (Hermes scan caution, installed with --force (library plugin))`, printed under `--quiet` too), and `--json` carries what Hermes printed for the plain install, its findings included, as that note's `diagnostic`: a caution is accepted, not called harmless. A `dangerous` verdict is never overridden: a red line, the links stay. Scanning itself is never turned off (`plugins.scan_on_install` stays as you set it). `status` does not show the verdict: Hermes records none in its files, and `status` reads only those. After the installs the read-back is hermes's own: `hermes plugins list` must show each plugin installed this run enabled and `git pinned@<commit>` at the release commit, and its install row must say the same; anything else is a red line and its links stay. A plugin already current (its version, skills and `NOTICE.md` the release's, enabled) is a skip, so a second run installs nothing and Hermes scans nothing. Hermes's home is `HERMES_HOME`, else `%LOCALAPPDATA%\hermes` on Windows and `~/.hermes` elsewhere; Hermes has no global instructions file, so no block, and no user hooks file, so no hook entry; a `hermes` missing from PATH is one line and nothing is installed or removed. `unlink` takes its plugins out again (`hermes plugins remove <id>`, below). Hermes lists a plugin's skills as `agent-plugin-<id>-<hash>:<skill>` (`/agent-plugin-oneezy-80c7eb0f:oneezy-status`).
- **What an older version left** is named, never read, never touched. `~/.skills-sync` as a link to a library checkout (the PC: the old tool pointed it at `--repo`) is one `.` note on every run: `~/.skills-sync (link -> V:\dev\skills) is the old library link; machine commands no longer use it; delete the link by hand, the checkout stays; its skills-sync.local.json is still used by library commands run inside that checkout` (`update`, `refresh` and `add` keep the skills found gone upstream there, `links` the link mode). A link to anything else is `the old library link; nothing reads it any more, delete it by hand`; the clone itself at `~/.skills-sync` is `the old library clone; ...`, and a `skills-sync.local.json` inside that clone gets its own line (`the old tool's answers file; ...`). The loose links an older version made in the user folders go when a harness's form takes them, or with `unlink` (see [unlink](#unlink)).
- **On another machine?** Run the same command there (or ask the agent to run the `oneezy-skills` skill, which does exactly that). The tool never edits a harness's settings: plugins go in through each harness's own plugin commands.
- **On Windows** the same sync runs inside every WSL distro (`wsl.exe -l -q` lists them on every run) through `npx --yes @oneezy/skills-sync@<this version> sync`, with this run's `--plan`, `--json` and `--quiet`: one `.` line per distro with the summary it printed (`WSL Ubuntu (synced: 0 changed, 2 already right, 0 left alone)`); a distro without Node is one note (`no npx in the distro; install Node there to sync it`), a sync that fails there one red line and exit 1. `SKILLS_SYNC_WSL_BIN` names another command to run inside the distros (a development build). `--json` carries each run under `wsl`.
- **In a cloud session** (`CLAUDE_CODE_REMOTE=true`) the run writes the global block and stops: no plugin command, no WSL, no loose links; claude.ai delivers the account plugins itself. The block needs no release, so GitHub out of reach there still writes it, with one note line and exit 0. The setup script line is a plain `npx --yes @oneezy/skills-sync@latest --quiet`; the older `-y --agents claude-code --global --no-projects --no-wsl --quiet` line does the same and names its old flags once on stderr.

An older flag on a machine command (`-y`, `--agents`, `--global`, `--no-projects`, `--no-wsl`, `--links`, `--plugins`, `--no-pull`, `--no-remember`, `--repo`, `--watch`, `--ask`, and the rest; see [Commands and flags](#commands-and-flags)) is accepted, does nothing, and is named in exactly one line on stderr: `ignored: --agents, --global, --no-projects (settings come from the release's skills-sync.json; machine facts are detected on every run)`. Output and exit code are otherwise the run's own, so an old setup script or hook keeps working. `projects`, `adopt-brain` and `rollback-brain` are retired: one line, exit 2. Node 20+; git only for the library commands.

A change reaches the machines through the library's release: edit the skill, push, let the library's CI cut the release, and every machine's next sync reads it.

## The library

A skills library is a folder with `skills/` beside `skills-sync.json`, `skills-sync.lock.json` or `skills-lock.json`:

| path | holds | written by |
|---|---|---|
| `skills/<name>/` | a flat own skill, bare Agent Skills form (`SKILL.md`, optional `scripts/`, `references/`, `agents/openai.yaml`) | you |
| `skills/<group>/<name>/` | an own skill inside a group; the group's name is its plugin id | you |
| `skills-sync.json` | the committed config: the library itself, the two generation switches, third-party sources with their selections, renames and pins, the plugins | you, `add` and `remove` |
| `skills-sync.lock.json` | what a config library has installed, per source as in the config: repo, ref, upstream version, commit, date, and each skill's upstream path and content hash (plus a commit where a pin holds it elsewhere) | `refresh`, `add`, `remove` |
| `skills-lock.json` | what a library without a config has installed, in the `npx skills` format. In a config library it is the lock skills-sync 0.4.0 wrote, which `refresh` migrates to `skills-sync.lock.json` | `npx skills add/update` |
| `plugins/<id>/` | the plugin form, one package per plugin in the config: skill copies, `plugin.json`, `.codex-plugin/plugin.json`, `.claude-plugin/plugin.json`, `LICENSE`, `NOTICE.md`. Committed. | `build` |
| `.claude-plugin/marketplace.json`, `.agents/plugins/marketplace.json` | the two marketplace catalogs, each listing `./plugins/<id>`. Committed. | `build` |
| `skills-sync.local.json` | a library command's memory on this checkout: the selected skills `update`, `refresh` or `add` found gone upstream (skipped until `--retry`) and the link mode (`links`) an older version set. Older versions kept this machine's answers here too; no machine command reads it. Gitignore it. | `update`, `refresh`, `add` |

A library with a config gets its third-party skills through `refresh` (see [Third-party sources](#third-party-sources)). A library with only `skills-lock.json` keeps `npx skills update` as the owner of its copies; `check` still reads it.

A folder directly under `skills/` that holds `SKILL.md` is a flat own skill. One without `SKILL.md` is a **group**: its children are own skills, and the group's name (`oneezy`, `trident`) is the plugin id they will be packaged under. A skill is known everywhere by its folder name alone, so `skills/oneezy/oneezy-status` links as `oneezy-status`, exactly as `skills/oneezy-status` would, and moving a skill into a group retargets its links without dropping any. Groups do not nest: a `SKILL.md` two levels below a group, or a second skill with a name already taken, is reported by `check` and never packaged.

The group named `play` is the playground: a place to try a skill (your own idea, or one copied from someone else's repo) before promoting it into another group. It is packaged, cataloged and linked exactly like any other group, and every skill in it is named `play-<name>` (`skills/play/play-unslop`, used as `/play-unslop`), so it never clashes with a skill from a source; `check` fails on one that is not. Other groups' skill names are not held to a prefix.

Everything else in it is generated and should be gitignored:

| path | holds |
|---|---|
| `upstream/<source>/<upstream path>` | snapshots: each source's selected skill folders and attribution files at their upstream paths, plus `.snapshot.json`. Never edited. |
| `.agents/skills/<name>` | the working set: one copy per third-party skill (from its snapshot, with its rename applied), which `build` packages. A link per own skill that an older version made there is left as it is; nothing makes them now. |
| `artifacts/` | the upload archives `build --artifacts` writes: one ZIP per plugin, `releases.json`, and a `<id>.changes.md` note when one is due (see [Artifacts](#artifacts)) |

`oneezy/skills` is one such library; `npx skills add oneezy/skills` installs its own skills anywhere, `/plugin marketplace add oneezy/skills` and `codex plugin marketplace add oneezy/skills` offer its plugins (see [Plugins and catalogs](#plugins-and-catalogs)), and one `npx @oneezy/skills-sync` on a machine gives it the whole set from the latest release, no clone needed.

## What a run does

`sync`, the default command, runs anywhere, with no library on the machine:

1. **Read the release.** The latest release of the library on GitHub (`--library owner/repo` for another; `GITHUB_TOKEN` or `GH_TOKEN` is sent when set, the base URL comes from `SKILLS_SYNC_GITHUB_API` so tests point it at a fake; behind a proxy, `HTTPS_PROXY` / `HTTP_PROXY` and `NO_PROXY` are honoured by the tool itself, through a CONNECT tunnel, so `NODE_USE_ENV_PROXY` is not needed on any Node; a redirect to another host goes without the token): its plugins, and the library's committed `skills-sync.json` at the release's commit, whose `machines` key holds the settings every machine takes (below). The global block needs none of it: GitHub unreachable still writes the block; outside the cloud it is one red line (the plugins cannot be judged) and exit 1, in the cloud one note and exit 0.
2. **Probe the machine.** Which harnesses have a config folder (`~/.claude`, `~/.codex`, `~/.hermes` (`%LOCALAPPDATA%\hermes` on Windows), or `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `HERMES_HOME`), which plugin CLIs are on PATH, and what each harness has: its account plugins, the plugins installed through its CLI, the loose links and real folders in its user skills folder, the block in its global instructions file. And what an older version left: `~/.skills-sync`, the `skills-sync.local.json` in it. Nothing is read from a file of the tool's own; there is none.
3. **Per harness, in table order.** A harness the release's config leaves out is one note (`not served: the release's skills-sync.json names harnesses claude-code; nothing changed here`). Otherwise the block in its global instructions file (see [The global block](#the-global-block)), outside the cloud its session hook entry (see [The session hook](#the-session-hook)), then its form (see [The forms](#the-forms)). A form's plugin commands run while the plan is made, outside `--plan`; the file changes (links removed, blocks written) are applied once the plan is complete, each checked against the file as it was.
4. **WSL.** Windows only: the same sync inside every distro, through the published package (above). Never from the cloud, never for `status` or `unlink`.

Then it prints one line per action (`+` made, `-` removed, `~` changed, `=` already right, `!` left alone, `.` a note) and a summary (`2 changed, 0 already right, 0 left alone`). `--plan` prints the same without touching anything and runs no plugin command that writes; `--quiet` prints only when something changed or is red, so a session start stays silent; `--json` carries the actions and the facts (`release` with its `config`, `cloud`, `oldLibrary`, `oldLocalFile`, `wsl`). Anything red is exit 1.

### The release's settings

The library's `skills-sync.json` may carry a `machines` key (shape in `schemas/skills-sync.schema.json`), read leniently at the release's commit:

```jsonc
"machines": {
  "harnesses": ["claude-code", "codex"],      // only these get the block and their form; absent: every harness detected
  "plugins": {                                 // the release plugins each harness takes, by harness id, "*" for the rest;
    "*": ["oneezy", "play"],                   // absent: every plugin the release ships; an id the release lacks is nothing
    "codex": ["oneezy"]
  }
}
```

A release whose commit has no `skills-sync.json`, or one the tool cannot read as JSON, serves every detected harness every plugin (`config: null` in `--json`). The catalog name the plugins come from on Claude Code and Codex is `<owner>-<name>` from `library` (`oneezy-skills`). A change to the file reaches every machine with the next release; nothing is set per machine, and a harness that disappears from the machine is absent from the next run's report.

### Retired: the Brain block (0.15.0)

`adopt-brain`, `rollback-brain`, `--adoption-file` and `--no-entrypoints` are gone, with the library's `skills-sync.entrypoints.json` and its schema. The global block points at `/oneezy-agents` (see [The global block](#the-global-block)), and the `/oneezy-brain` skill owns Brain routing. Either command is one line on stderr and exit 2; either flag is accepted and does nothing, and a machine command names it in its one `ignored:` line. `check` no longer reads an entrypoints manifest. An old `brain` block in a global instructions file is still replaced by `sync`, as below.

### Explicit historical Skills/Status alias handoff (0.7.4)

`migrate-aliases --alias-file <manifest> --receipt <durable-json> --repo <verified-library> --expect-revision <full-sha> --remote-ref <exact-ref>` handles only the historical `oneezy-skills` and `oneezy-status` aliases in Justin's Windows `.agents/skills` and `.claude/skills`, or Ubuntu `/home/justin/` equivalents. The version 1 manifest supplies literal `path`/`expectedTarget` pairs at `V:\dev\skills\skills\oneezy\<skill>` or `/mnt/v/dev/skills/skills/oneezy/<skill>`. Preview with `--plan --json` first.

The enabled native plugin must match this library's registered source/version, expose the exact skill, and carry all reviewed files before an alias moves. Every selected alias on a harness passes preflight together. The tool rechecks immediately before mutation and moves the original link into `.skills-sync-alias-backups` under that harness's config directory, outside skill discovery. The receipt records replacement hashes and backup ownership. Independent harnesses can succeed while a failed prerequisite holds the other. This command does not pull, install plugins, remember choices or write instructions. Ordinary sync still preserves foreign links.

For a pinned migration, pass `--expect-revision <full-commit-sha> --remote-ref refs/tags/<release-tag>`. The default remote ref is `refs/heads/main`. The selected HEAD, clean authored/generated library files, and origin's exact ref (peeled for annotated tags) must all agree before an alias moves. Missing access or a mismatch refuses the migration; it never changes Git configuration or replaces dirty work.

Repeat with the same manifest/receipt to verify idempotence. `rollback-aliases --repo <library> --receipt <receipt> [--plan --json]` restores only unchanged preserved aliases, refuses later destination edits and retains installed plugins. Keep receipts and backups durable. Verify fresh default discovery and actual Skills-to-Status execution separately from installed-file checks.

Claude write commands negotiate `--json` from their own `--help`; older versions with JSON listings but no JSON writes remain supported. Failed native commands retain structured `diagnostic.command`, `exitCode`, `stdout` and `stderr` on their conflict actions, with credential-bearing transport text redacted. No settings patch is used to hide failures.

### Links

Every link is a directory symlink. On Windows a symlink needs Developer Mode or elevation; when the system refuses one (EPERM) the tool makes a junction instead and says so in the run's `links:` line. For the library command that makes links (`migrate-aliases`), `--symlinks` makes symlinks only (the run fails where one is refused), `--junctions` makes junctions only; a `links` key in the checkout's `skills-sync.local.json` is read as the default. A machine command makes no link: it removes the tool's, and a link that already points at the right folder is left as it is, whatever its kind. POSIX has only symlinks.

## Third-party sources

Third-party skills come from **sources** declared in `skills-sync.json`. The config is yours to edit; `add` writes an entry for you. Its shape (the full rules are in `schemas/skills-sync.schema.json`):

```jsonc
{
  "version": 1,
  "library": { "name": "skills", "owner": "oneezy", "homepage": "https://github.com/oneezy/skills" },
  "generate": { "skills": true, "plugins": true },   // the two forms, each behind a switch; both true when absent (read by build)
  "renderings": { "hermes": "dist/hermes" },         // opt-in: the Hermes rendering of every package, at that folder (read by build)
  "sources": {
    "matt-pocock": {
      "repo": "mattpocock/skills",          // owner/repo, a git URL, or a local path
      "ref": "main",                        // the branch or tag followed: its tip at every update
      "version": "1.3.0",                   // optional: hold the source at this upstream release; latest when omitted
      "root": "skills",                     // where the skill folders live (searched three levels deep, like npx skills)
      "skills": ["tdd", "writing-for-agents"],                                         // a list: these, and update names the rest
      "pins": { "writing-for-agents": "321658273cb1d20b76026717d027d505790106d4" },   // one skill held at its own commit
      "attribution": ["LICENSE", "README.md"]                                          // carried into the snapshot and every package
    },
    "pstack": {
      "repo": "cursor/plugins", "ref": "main", "root": "pstack/skills",
      "skills": "*",                                                                   // every skill folder under root, now and later
      "rename": { "tdd": "pstack-tdd", "teach": "pstack-teach" },                      // beside "*" only: taken under another name
      "attribution": ["pstack/LICENSE", "pstack/README.md"],
      "adapt": {                                                                       // optional: find/replace for another harness's wording
        "rules": [{ "find": "the `Task` tool", "replace": "your subagent tool" }, { "find": "AskQuestion", "replace": "your question tool" }],
        "forbid": ["\\bAskQuestion\\b", "`Task`"],                                    // none may be left in a package once the rules ran
        "allow": ["^- Cursor's docs list Custom Modes"]                                   // lines that may keep a forbidden term
      }
    },
    "picked": {
      "repo": "someone/skills", "ref": "main",
      "skills": { "tdd": "picked-tdd", "why": "why" }                                  // a map selects and renames on import
    }
  },
  "plugins": {
    "oneezy": { "displayName": "Oneezy", "description": "Justin's own skills", "group": "oneezy" },
    "pstack": { "displayName": "PStack", "source": "pstack" }
  }
}
```

**What a source selects.** `skills` is a list of upstream folder names, a map from upstream name to working-set name (a rename), or `"*"`: every skill folder under `root` at the source's commit, so a skill upstream adds is taken on the next `update` and one it removes leaves, with no list to keep. Beside `"*"`, `rename` maps the upstream names taken under another name (`"tdd": "pstack-tdd"`); the schema refuses `rename` beside a list or a map. A source that selects by a list or a map is told, on every `update`, each skill folder under its root it does not select: one line per source, `pstack: not selected upstream: correct, poteto-help (select them in skills-sync.json, or take every skill under the root with "skills": "*")`, printed on stderr whatever the flags (`--json` and `--quiet` included; under GitHub Actions as a `::warning::` workflow command, so the library's daily update run shows it on its page) and carried in `--json` as `unselected` (`source:name`, like `gone`). It is a warning, never an exit code: the daily run lands nothing when `update` fails, so a source that leaves a skill out on purpose would otherwise hold every other source back. A name only `"*"` brings in (not yet in that source's lock, not a `rename` or a pin) never displaces a skill another source ships or an own skill: the folder is left out, not snapshotted or locked, and named the same way, `pstack: not taken from upstream, the name is already another's: grilling (matt-pocock); give each a "rename" to take it`, and in `--json` as `shadowed`. A `rename` that gives two of a `"*"` source's folders one name (onto a folder upstream also has, or two renames onto one name) is refused for that source with the reason, exit 1. Under `--json`, every conflict the run reports (one name from two sources, an own skill in the way) is printed on stderr too.

**Latest is the default.** Every selected skill is taken at the tip of its source's `ref` on each `update`; `sync` never moves one. A **held version** is the first exception: a source with `"version": "1.3.0"` is taken at that release (the commit of its tag, or for a source versioned by its manifest the newest commit on `ref`'s history whose manifest carried that version) until the config changes; plain semver only, `v1.3.0` is refused by the schema. A **pin** is the second: a skill listed in `pins` is taken at that commit while its siblings move; change the commit to move it, remove it to let it follow. A `ref` that is a full commit holds the whole source. The tool never writes `version` (or anything else in `skills-sync.json` but what `add` declares and `remove` takes out): `update --to` prints the change and whoever lands it commits it. The `generate` switches say which forms the library builds (the loose-skill layers, the plugin packages); `build` reads `generate.plugins`.

**`update [<source>...]`** (`refresh` is the same command, kept for scripts and CI) resolves the named sources, every one when none is named, and makes the library match. A source not named resolves frozen, as `sync` does: its lock entry stays byte for byte and its working copies at the commits the lock records. For each named source:

1. Each source's commit: the tip of `ref` (one `git ls-remote`), or `ref` itself when it is a commit; with a held `version` (or `--to`, below), that release's commit, found in a blobless clone of `ref` with its tags. With `--frozen` every skill is taken at the commit `skills-sync.lock.json` records for it (a `skills-lock.json` from 0.4.0 is read in its place, unchanged), a skill the lock does not record is left alone and reported, and no lock is written; this is what CI runs, and what every `sync` runs.
2. What upstream has under `root` at that commit: the list `.snapshot.json` recorded while the commit stands, else a temp clone's (one the move needs anyway, or once for a snapshot written before 0.10.0). A `"*"` source selects all of it (its pins too, renames applied); a list or a map gets the `not selected upstream` line above for the rest. Each selected skill is found under `root` by folder name, at its pin when it has one. When the snapshot already holds that commit's content (its hash matches the lock) nothing is fetched; otherwise a temp clone is staged (blobless, with the history and tags behind that commit) and deleted when done. A skill not found upstream is reported once as gone, remembered in `skills-sync.local.json`, and not looked for again until `--retry`.
3. The snapshot `upstream/<source>/` gets the skill folders and attribution files at their upstream paths, and a `.snapshot.json` (source, repo, ref, commit, date, version and commits past it, skills with their path, hash and commit, `upstream`: every skill folder name under `root` at the commit, attribution). Folders no longer selected are deleted. Snapshots are generated and never edited; gitignore `upstream/`.
4. The working set: `.agents/skills/<name>` becomes a copy of the snapshot folder, under the new name with the frontmatter `name` rewritten when renamed. A copy whose files already match is skipped; a copy no longer selected is deleted. One name selected by two sources: the first source by id wins and owns the lock entry; the other is reported until the config renames it. An own skill with the same name keeps it.
5. `skills-sync.lock.json` is written (never with `--frozen`), version 2, grouped per source like the config, sources and skills sorted:

   ```json
   {
     "version": 2,
     "sources": {
       "mattpocock": {
         "repo": "mattpocock/skills",
         "ref": "main",
         "version": "1.3.1",
         "commit": "<40-hex commit>",
         "date": "<the commit's ISO date>",
         "skills": {
           "tdd": { "path": "skills/engineering/tdd", "hash": "<recipe sha256>" },
           "writing-for-agents": { "path": "skills/writing-for-agents", "hash": "<recipe sha256>", "commit": "<its pin>" }
         }
       }
     }
   }
   ```

   Skills are keyed by their working-set name (a rename shows here) with their upstream path; a skill carries a `commit` only when a pin holds it at another commit than its source's. A `skills-lock.json` that skills-sync 0.4.0 wrote (every entry with a `commit`) is migrated once: the new lock is written, the old file removed, one line says so. An `npx skills` lock of its own is never touched.

**Versions.** A source's version is plain semver (`1.3.1`, never `v1.3.1`), resolved at its commit in this order: the nearest release tag at or before it (a leading `v` or `name@` stripped; pre-release tags only when no stable one is reachable); else the `version` of the nearest of `.claude-plugin/plugin.json`, `.cursor-plugin/plugin.json`, `.codex-plugin/plugin.json` and `package.json`, looking in the source's `root` and then each parent up to the repo root; else none (`null`). Output names each source by its version and how far past it the commit is, `mattpocock: 1.3.1 (+4 commits)`, counted from the tag's commit or from the commit that set the manifest to that version; a source without a version shows its date and short commit. The lock stores only the version and the commit; `--json` carries `version` and `ahead` (the count) per source.

The hash is the `npx skills` recipe (SHA-256 over every file's relative path then bytes, sorted by `localeCompare`), computed over bytes exactly as upstream committed them, so a lock written on one machine verifies on any other. `refresh --plan` shows the actions without touching the library (it still stages clones in the temp folder). `--json` adds `sources` (per source: `commit`, `date`, `version`, `ahead`, `moved`), `updated`, `config` (both above), `gone`, `unlocked` and `problems` to the usual actions. A source that cannot be reached keeps its lock entries and snapshot, and the exit code is 1.

Every source whose commit is not the one the lock had is reported, from and to, as `updated up: 1.2.0 (+1 commit) 4f2a9c1 -> 1.3.0 8d0e3b7` on stdout and in `--json` as `updated: [{ id, from: { version, commit, ahead }, to: { version, commit, ahead }, direction, changelog, changelogReason? }]` (`from` is null for a source new to the lock; `ahead` is null where it is not known). A source that did not move is not in it.

With each one comes what upstream's `CHANGELOG.md` says between the two versions, so breaking changes and migration notes are seen: the whole sections whose version heading (`## 1.3.0`, `## [1.3.0] - 2026-10-01`, `## v1.3.0`, matched as plain semver) is above the lower version and at or below the higher one, in the file's order, read at the higher side's commit from the `CHANGELOG.md` nearest the source's `root` (that folder, then each parent up to the repo root). 1.2.3 to 1.3.1 gives the 1.3.1 and 1.3.0 sections; a downgrade, 1.3.1 to 1.2.3, gives the same range as the one it undoes (`direction: "downgrade"`, else `"upgrade"`). On stdout the sections follow the `updated` line, indented under `changelog after 1.2.3 up to 1.3.1:` or `undoes the changelog after 1.2.3 up to 1.3.1:`. `changelog` is null, with `changelogReason` (printed as `changelog: none (<reason>)`), when there is no `CHANGELOG.md` upstream, either version has no heading in it, either side has no version, both sides are the same version, or the source is new to the lock.

**`update <source> --to <version>|previous|latest`** moves one source (`--to` with no source, or with two, is refused):

- `--to 1.3.0` takes that release, as a held version would; a leading `v` is accepted.
- `--to previous` takes the highest stable release below the version the lock records: the next lower tag, or for a source versioned by its manifest the newest commit carrying the next lower distinct version.
- `--to latest` takes the tip of `ref`, past any held version.

The config is not written. The change that makes the move stick is printed for the caller to land, `skills-sync.json: sources.up.version = "1.3.0"`, or `remove sources.up.version` for `latest` when a version is held (nothing when the config already says so); `--json` carries it as `config: [{ source, version }]`, `version` null for a removal. Until it lands, the next plain `update` puts the source back where the config says. A version the source has not released, or `previous` below its lowest release, is refused with the versions it has, newest first, `up: 1.5.0 is not a release (versions: 1.3.1, 1.3.0, 1.2.3)`; nothing is written and the exit code is 1 (`--json`: `{ "refused": "..." }`).

**`versions <source>`** lists what a source has released on `ref`'s history, highest first, each with its commit and date, the one the lock is at marked `*` with how far past it the lock is. Release tags when any is reachable (stable ones only, unless there are none; `v1.3.0` over `skills@1.3.0` when both name a version), else each distinct version of the manifest that versions it, at the newest commit carrying it. `--json`: `{ source, repo, ref, current: { version, commit, ahead }, versions: [{ version, commit, date, current }] }`. It stages a temp clone and writes nothing.

**`add <source>`** declares a source and brings its skills in: `add mattpocock/skills`, `add cursor/plugins#main --root pstack/skills --skills '*' --as tdd=pstack-tdd,teach=pstack-teach` (writes `"skills": "*"` with the `rename` map, so the source follows upstream), `add ../some/repo --skills a,b`. It stages the repo in a temp clone, lists the skills under `--root` (default `skills/` when the repo has one, else the root), writes the config entry (`--id`, default `owner-repo`; the default branch unless `#ref`; every skill unless `--skills`; a map when `--as` renames; the nearest `LICENSE` and `README.md` as attribution) and the plugin entry that packages it (`--plugin <id>`, default the source id, display name from the id; `--no-plugin` for none; an id already in `plugins` is refused before anything is written), and resolves that one source with that clone, as `update <source>` would: every other source stays exactly where the lock has it, and the new one is reported as updated. `build --plugins --catalogs` then writes the package. Nothing is installed anywhere: no agent folder, no `~/.skills-sync`, no `npx skills` run against the library. `add --plan` prints the entries it would write and stops. Add a pin or drop a skill by editing the config, then `refresh`.

**`remove <source>`** is `add` in reverse: `remove diagram-design`, `remove cathrynlavery/diagram-design`, `remove https://github.com/cathrynlavery/diagram-design`. It takes the source id, or the `owner/repo` (or GitHub URL, any case) of exactly one source; an id it does not know, an `owner/repo` that two sources share, an authored group (`remove oneezy`) or a plugin id (`remove frontend-design` says to `remove anthropic`) is one line and exit 2. The source leaves `skills-sync.json` with every plugin whose `source` it is (a plugin with a `group`, or without a `source`, is never taken), its entry leaves `skills-sync.lock.json`, and its snapshot under `upstream/` and its working-set copies in `.agents/skills` go (never an own skill's name, never a link). Then it runs `build --plugins --catalogs` on the config as written: the packages under `plugins/<id>/`, their Hermes renderings and their catalog entries go, so `check` is clean and the next release drops the source from every harness. A source whose plugin `machines.plugins` still lists, or that `releases` records an upload of (take it out of ChatGPT by hand first), is refused, exit 1, naming each place. Nothing is written on a refusal, and nothing is cloned: `remove` is offline. `remove --plan` lists every write and delete, the build's included, and writes nothing; `--json` carries them with `removed` (`source`, `repo`, `ref`, `plugins`, `skills`).

**Adapting a source (`adapt`).** Skills written for one harness (pstack is written for Cursor) name that harness's tools and paths. A source's `adapt` block holds plain find/replace rules that `build` applies as it copies the source's skills into `plugins/<id>/`, so every rendering made from the package (the Hermes one, the upload archives) carries the same text. No model or agent takes part: the rules are string work on bytes, and the same input gives byte-identical output, so `build --check` stays clean.

- `rules`: `{ "find": "<regex>", "replace": "<text>", "flags"?: "i" }`, applied in order to every Markdown and text file (`.md`, `.mdc`, `.markdown`, `.txt`; one whose bytes are not UTF-8 is copied as it is) of the source's skills, each rule to the text the one before it left. `find` is a JavaScript regular expression and every match is replaced (`g` is implied; `flags` adds `i`, `m`, `s` or `u`); `replace` takes `$1`, `$<name>` and `$&` as `String.prototype.replace` does, `$$` for a dollar sign. The frontmatter is text like the rest, so a rule can fix a `name` or a `description` too. Scripts (`.sh`, `.py`, `.js`, `.ts`, `.ps1`), data (`.json`, `.yaml`) and every other file are copied as upstream wrote them, and the snapshot under `upstream/`, the working set under `.agents/skills/` and the lock never see a rule: a skill's hash is still upstream's.
- `forbid`: regular expressions (case-sensitive) that no adapted file may still match once the rules ran. Each match left fails `check` (`plugins/pstack/skills/arena/SKILL.md: line 17: forbidden term "Task" (sources.pstack.adapt.forbid: \bTask\b) is left after the adapt rules; add a rule for it, or an allow for the line`) and `build --check` (a `forbidden    <path>:<line>: "<term>"` line, exit 1); a plain `build` writes the package and prints the same line. Lines count in the package file, whose `SKILL.md` carries `metadata.internal`. `--json` carries them as `forbidden` (`source`, `path`, `line`, `term`, `pattern`).
- `allow`: regular expressions tested against each line of an adapted file (without its line ending); a line one of them matches may keep a forbidden term, such as a factual "(in Cursor: `~/.cursor/projects/...`)". A pattern matches anywhere in the line, so anchor it with `^` and `$` to accept only that exact line.

A rule that matches nothing in any file of the source is a `note` from `build`, `build --check` and `check` (`sources.pstack.adapt.rules[4] (find "...") matches nothing in pstack's skills; fix it or remove it`; `unusedRules` in `--json`), never a failure, so a rule upstream made stale surfaces. `update` warns, never fails, on stderr (a `::warning::` under GitHub Actions) and in `--json` (`forbidden` as `source:skill/file:line: term`, `unusedRules`), when a forbidden term is left after the rules in a skill whose content the update brings new, and when a rule matches nothing in the source at its new commit: the daily run names a new term before `check` fails on it. A pattern that is not a regular expression is a `check` problem on `skills-sync.json` and a conflict that leaves the package unbuilt. When a rule matched, the package's `NOTICE.md` gains one line, `- Adapted: <n> find/replace rules from sources.<id>.adapt in skills-sync.json rewrote the Markdown and text files; ...`, `<n>` counting the rules that matched. Without an `adapt` block the build is byte for byte what it was; an older tool refuses the key (`$.sources.pstack.adapt: not allowed`), so a library adds it only once this version is on npm.

## Plugins and catalogs

The same library is a plugin marketplace for Claude Code, Codex and ChatGPT. **`build`** writes the plugin form into the library, beside the source, and the result is committed like any other change; nothing is generated at install time and CI only checks. It runs when the config's `generate.plugins` is true (the default); with it false, `build` writes nothing and `build --check` ignores the plugin form.

`build --plugins` writes one package per entry of `plugins` in the config:

```
plugins/<id>/
  plugin.json                  Agent Plugins 1.0: $schema, name, version, description, author, homepage, repository, license,
                               keywords, and the ChatGPT interface under extensions["com.openai"] (displayName, shortDescription,
                               longDescription, developerName, category, capabilities)
  .codex-plugin/plugin.json    the legacy flat form of the same, plus skills: "./skills/" and interface
  .claude-plugin/plugin.json   name, displayName, description, author, license, homepage, repository, keywords; no version,
                               so Claude Code tracks the library's commits
  skills/<name>/               a copy of each skill: an own group's skills from skills/<group>/, a source's selected skills
                               from the working set (renames applied)
  LICENSE                      the source's LICENSE from its attribution files; for an own plugin the library's LICENSE
                               when it has one, else none and one reported line
  NOTICE.md                    the source repo, the commit and date the files were taken at, the license, the skills
                               (renames and per-skill pins noted), and why the copies are marked internal
```

Every copied `SKILL.md` gains `metadata.internal: true` in its frontmatter (into an existing `metadata:` map, or a new one at the end; nothing else in it changes). `npx skills` skips a skill so marked, so a consumer of the library installs and updates each own skill from `skills/` exactly once rather than finding it twice; `INSTALL_INTERNAL_SKILLS=1` re-exposes the copies. `build --check` compares after that transform.

Hermes rejects that flag: its portable plugin loader takes a skill's `metadata` only as a map of strings, and skips the skill otherwise. So, for a library that opts in with `"renderings": { "hermes": "dist/hermes" }` in `skills-sync.json`, `build --plugins` also writes a **Hermes rendering** of each package at `dist/hermes/<id>/` (the folder the key names; the machine sync installs from the folder the release's `skills-sync.json` names, and from `dist/hermes` when it names none): the same `plugin.json`, `LICENSE`, `NOTICE.md` and skill folders, without the `.claude-plugin/` and `.codex-plugin/` manifests, each skill's root `SKILL.md` with `name` set to its folder and `metadata` cut to its string entries (`internal`, nested maps, lists, numbers and booleans go; an empty map goes). Every other file is byte for byte the package's, so the release's sha256 of `NOTICE.md` tells whether an installed Hermes copy is the release's package. `hermes plugins install <owner>/<name>/dist/hermes/<id>` installs it (the machine sync does, at the release commit); Hermes lists its skills as `agent-plugin-<id>-<hash>:<skill>`. A skill Hermes would still skip (a description over 1024 characters, a folder name that is not a lowercase hyphenated name) is a note; the copy is written all the same so its siblings load. The rendering is reconciled like the package: `build --check` lists a hand-edited or stale copy as drift, a link inside is a conflict, and a package that is no longer in the config loses its rendering with it. Without the key, `build`, `build --check` and `check` are byte for byte what they were, NOTICE.md included: a new output ships behind a library opt-in, so the publish guard (this build's `--check` against the library's main, ADR-0008) stays strict until the library takes it. The order is fixed by the validator: a tool version that knows an opt-in key must be on npm before the key lands in the library, because an older tool refuses an unknown key (`skills-sync.json is not a valid config: $.renderings: not allowed`) and the library's CI, which runs the npm release, stops at `refresh --frozen` until then. `npx skills add` never lists `dist/`, and release.json does not record the rendering: the package's `files` are what it verifies.

The version in `plugin.json` and `.codex-plugin/plugin.json` comes from the package's owner. A third-party plugin uses its source's locked upstream version, with a leading `v` and build metadata removed. A source with no published semantic version stays unversioned: the manifests omit `version`, the archive uses `-unversioned.zip`, and the release record stores `null`. A build never fabricates an upstream version.

An authored plugin uses the explicit `library.version` in `skills-sync.json` (plain `MAJOR.MINOR.PATCH`). Every authored plugin in that repository shares it. Set it before the first build and bump it deliberately for a release; a build neither counts changed files nor increments any component. Missing authored versions are conflicts. Keep the source commit and date in `NOTICE.md` and artifact records, separate from the version.

Unchanged inputs preserve their recorded provenance, so repeated builds are byte-identical even after committing the generated files, squash merges or shallow clones. Legacy generated versions are replaced by the declared or locked version on the first build. Existing NOTICE commits and dates remain checked when the checkout has that commit.

The reusable release calculator is `node scripts/release-version.mjs <current> <message>... --require-emoji`. It accepts titles such as `🐛 fix(sync): preserve upstream versions (#135)`: `fix` bumps patch, `feat` bumps minor, `!` or a `BREAKING CHANGE:` footer bumps major, and other conventional types do not bump. It selects the highest bump once across the release. Scope, issue number and emoji do not change the bump. It prints `{version,bump}` and does not edit files, tag or publish. Stable versions only; release automation and prerelease policy remain tracked in oneezy/tools#135 and layerdbiz/tridentcubed#157.

A package that cannot be built is a conflict: a source that is not in the config, a source with no snapshot under `upstream/` (a clone before `refresh`), a link inside `plugins/<id>` (never followed, never written through). `build` leaves whatever `plugins/<id>` holds and exits 1; `build --check` lists `plugins/<id>` as drift. A link inside a source skill folder is not copied, with a note.

A group the config declares as a plugin but that holds no skill yet (a new, empty `play`) is not a conflict: `build` and `build --check` skip it with one note (`no skills under skills/<group> yet; not built, not cataloged`) and exit 0, and the catalogs leave it out. When a group's last skill goes, `build` removes its `plugins/<id>` with that reason, and until then `check` reports the package as drift.

A package holds LF line endings, whatever the checkout it was built in holds. A source file (a skill's file, the LICENSE) whose line endings are all CRLF is copied with LF: that is what `core.autocrlf=true` makes of a committed LF file, and copied as read it would give a different package, and a different archive, from the same commit, with shell scripts that fail on Linux. A file committed with CRLF is copied with LF too, the library's or upstream's; a binary file (a NUL byte, or more than one control character in 128 bytes) and a file with mixed line endings are copied as they are. Every file `build` writes is therefore LF; on a checkout where git converts to CRLF a committed file is compared as git sees it, so such a clone is as built and `build` rewrites nothing there. Give the library a `.gitattributes` with `* text=auto eol=lf` so every clone holds LF regardless of the machine's git settings.

`build --catalogs` writes the two root catalogs, each listing every plugin with a `./plugins/<id>` source, in the config's order: `.claude-plugin/marketplace.json` (`name` is `<owner>-<name>` from `library`, `owner`, `description`, `plugins[]` with `name`, `source`, `description`) and `.agents/plugins/marketplace.json` (Codex: `name`, `interface.displayName`, `plugins[]` with `name`, `source`, `description`, `policy` `installation: AVAILABLE` and `authentication: ON_USE`, `category`). `build` with no output flag writes both: the committed form. The upload archives are a third output, written only when `--artifacts` asks (see [Artifacts](#artifacts)).

**`build --check`** computes every output in memory, prints each path that differs from disk (a hand-edited copy, a source edited since the last build, a missing catalog, a stale package, a package that cannot be built), writes nothing, and exits 1; a clean library exits 0. `--check --plugins` or `--check --catalogs` narrows it to one form. It never looks at `artifacts/`. CI runs `build --check` on every push so a skipped local build cannot land drift; the default shallow checkout is enough for it. `build --plan` shows the writes without making them.

Plugin skills run namespaced: `/oneezy:oneezy-status` in Claude Code, `$oneezy:oneezy-status` in Codex; their folder names do not change. Each package passes `claude plugin validate` (the only warning is the missing Claude version, by design) and the root passes it as a marketplace.

## The forms

Each harness gets the library's skills one way (ADR-0007 in `oneezy/skills`), never two, so no skill name is listed twice:

- **Claude Code: account plugins.** claude.ai delivers the plugins enabled on the account as `<id>@synced`; the tool installs nothing there and removes what hides or duplicates a delivered plugin (see the Claude Code bullet at the top).
- **Codex: plugins from GitHub.** The library's marketplace added from GitHub and each release plugin installed through `codex plugin`.
- **Hermes: plugins from GitHub.** Each release plugin's Hermes rendering installed from the release commit through `hermes plugins install owner/repo/dist/hermes/<id> --ref <commit>` and enabled, verified through `hermes plugins list` and the installed folder (see the Hermes bullet at the top). Hermes has no marketplace: a plugin's origin is the repository URL hermes recorded for it.

A form takes its plugin list from the release's settings (`machines.plugins`, above). The harnesses write their own settings while they install (Claude Code's `extraKnownMarketplaces` and `enabledPlugins`, Codex's `[marketplaces.*]` and `[plugins.*]`); that is the harness's doing through its supported command, not an edit by this tool. Nothing records what the tool installed: a plugin from the library's catalog (`<id>@oneezy-skills`) is the tool's, one from anywhere else is not, and a loose link is the tool's when it points into a library checkout or clone, at `~/.skills-sync`, or at nothing.

### unlink

`unlink` takes away what this tool put on the machine, and only that, per detected harness: the plugins installed from the library's catalog (`claude plugin uninstall <id>@oneezy-skills --scope user`, `codex plugin remove <id>@oneezy-skills`) and the catalog's registration once none of them remains (Claude Code's remove takes the catalog's plugins with it, so never while one stays); on Hermes, which has no marketplace, the plugins hermes recorded as installed from the library repository (`hermes plugins remove <id>`; a plugin without an install row, or from another repository, stays); every loose link in its user skills folder (Codex's old `~/.codex/skills` too) that points into a library checkout or clone, at `~/.skills-sync`, or at nothing; its session hook entry in the harness's user hooks file, the file itself when it held nothing else (the file is re-serialised as it was written, so every other entry stays as it was); and the skills block in its global instructions file, the file itself when it held nothing else (a `delete` line; a file that keeps text of yours is backed up beside itself first, as `sync` does). Account plugins, plugins from other marketplaces, a link to anywhere else, a real skill folder, another hook entry, Codex's trust record in `config.toml`, a block in a repository file and the text around the block stay byte for byte, but for one blank line before a block that ends the file (below). It reads no release, so it works offline, and names the old leftovers as `sync` does. `--plan` lists every removal and makes none, running no plugin command that writes. A plugin the CLI refuses to uninstall is one red line with the CLI's words; its marketplace stays, the rest still goes, exit 1. A second `unlink` has nothing to do; a `sync` after it puts the block and the hook entry back and nothing of the old state. A block that ends the file goes with the blank line before it, the one `sync` put there when it appended the block, so a file that ended in one line break is as it was; a blank line of your own in that place goes too, since `unlink` cannot tell the two apart. `--library owner/repo` names the library whose checkouts and catalog (`owner-repo`) count, as for `sync`; names are compared without case, as GitHub compares them. Since `unlink` reads no release, a catalog the library's `skills-sync.json` names other than `owner-repo` is not seen; remove such a catalog's plugins with the harness's own commands. Two things to know: `unlink` runs on this machine only, so on Windows run it inside each WSL distro too (the sync there put a block and a hook entry); and Codex trusts hooks by their position in `~/.codex/hooks.json`, so when another `SessionStart` entry follows the tool's, removing the tool's moves it up one and Codex asks you to review that entry again.

**status** is a machine command (below): it compares what each harness has with the latest release of the library on GitHub, not with a checkout.

## The global block

`sync` writes one managed block into each harness's global instructions file, `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` (Hermes has no such file in the harness table yet), between `<!-- skills-sync:skills:start built-in sha256:<hex> -->` and `<!-- skills-sync:skills:end -->`, on every machine, in every WSL distro (the same sync runs there) and in the cloud. Its text is the tool's own pointer (oneezy/tools#205, ADR-0017 in oneezy/skills): at the start of every session, load the `/oneezy-agents` skill and follow what it loads, which is Justin's rules (`skills/oneezy/agents.md` in the library); then how to call a skill in each harness and never fetch a `SKILL.md`. Only its line endings follow the file's. The start marker carries `built-in` and the sha256 of the text (LF line endings, ending in one line break). From 0.12.0 to 0.15.0 the text was the library's `SHARED.md` at the latest release's commit, stamped with that release; such a block is stale now and the next `sync` replaces it.

A block is rewritten only when its text differs from this tool's (by the sha256 in its stamp), when it was edited by hand, or when it is an older block, so a machine is not rewritten (or backed up) for every release. Before a write changes a global file that exists, the file is copied beside itself as `CLAUDE-backup-<UTC yyyymmdd-HHMMSS>.md` or `AGENTS-backup-<UTC yyyymmdd-HHMMSS>.md`, and the write's line names the copy; a name already taken (two changes in one second) gets `-2`, `-3`, never an overwrite, and the tool never deletes a backup. A new file has nothing to back up. The block needs no release: when GitHub cannot be read it is written all the same; in the cloud one line says the release was not read (`. note  oneezy/skills  (latest release not read: …; the global block needs none)`), printed even under `--quiet`, never a conflict.

The text between the markers is compared with its stamp byte for byte (line endings read as LF). Anything that rewrites it, a hand edit or a formatter re-aligning a table in `CLAUDE.md`, makes the block hand-edited: `status` says so, and the next `sync` restores it after one backup. Two runs at once (a session hook and a manual sync, two sessions starting) do not interleave: each write takes `<file>.skills-sync.lock` (made exclusively; one older than a minute is left by a run that died and is taken over, first renamed to a name of the taking run's own so two runs cannot both take it) around the hash check, the backup and the rename, and the run that finds it taken skips that file silently. The new text goes to a temp file of the run's own first, then the backup, checked against the file as planned (a mismatch leaves the file alone, one line), then the rename into place; a failed write leaves neither the temp file nor its backup behind. A temp file (`<file>.skills-sync.<pid>.<random>.tmp`) older than a minute, left by a run that died before its rename, is deleted by the next `sync` (`--plan` names it).

Only the bytes between the markers change. A marker is a whole line, a byte order mark before it on line 1 allowed (and kept), and its id is the tool's, `skills` or the old `brain`: a `<!-- skills-sync:example:start -->` of your own, in a fenced example, is text like any other. An older block (the `brain` block earlier versions wrote, or the unstamped `skills` block of 0.11 and before) is replaced where it stands, after its backup, everything around it stays byte for byte, line endings included, and a second run changes nothing. A file with broken markers or two managed blocks is left alone and reported. The block is never written into a repository's `AGENTS.md`, `CLAUDE.md` or settings; one an older version left there (in the current folder, where its harness would read it; a project the old answers file remembered is not looked at, that file is never read), or in a second global file such as `~/.codex/AGENTS.override.md`, is a `note` line on every run until someone removes it by hand. `--plan` shows the writes and the backups they would make, and makes none; `--json` carries them as `write`/`skip`/`conflict` actions (a write's `backup` names its copy) beside `release`, `error`, `cloud` and `block`: the text this run writes, `{ stamp, sha256 }`.

## The session hook

Outside the cloud, `sync` also keeps one session-start hook entry per harness: a `SessionStart` group in Claude Code's `~/.claude/settings.json` (or under `CLAUDE_CONFIG_DIR`) and in Codex's `~/.codex/hooks.json` (or under `CODEX_HOME`), matcher `startup|resume`, running `npx --yes @oneezy/skills-sync@latest hook` with a 120 s timeout (Codex's entry also carries `statusMessage: "Skills Sync"`). The tool knows its entry by that command, whatever the version suffix, never by its place in the list, so a second run adds nothing; an entry pinned to a version (`@0.8.0 hook`) is recognised and left as it is, never rewritten to `@latest`, so the trust Codex gave it survives. Every other entry and key is left byte for byte as it was: the file is re-serialised with its own indentation, line endings and trailing newline, and the new group is appended at the end (Codex trusts a hook by its position, so nothing is reordered). The old hand-made `sync-dev.sh` entry is removed only in a run where the new entry already exists or was just written and read back; a hooks file that is not valid JSON is a conflict line and left alone, old entry included. A cloud session writes no hook: it never reads user hooks. The entry is written for the machine the sync runs on; a WSL distro gets its own when the sync runs inside it.

Codex runs a user hook only after you trust it once, in its TUI, per machine or distro: run `codex`; on the `Hooks need review` screen choose `1. Review hooks` (or type `/hooks`); select `SessionStart`, then the row `[!] Skills Sync · new`, and press `t`; Esc twice. The hook runs from the next `codex` start. Codex records that trust in `~/.codex/config.toml` as `[hooks.state."<key>"]` with a `trusted_hash`, and runs the hook only while that hash is the hash of the entry as `hooks.json` has it now; an entry that changed since (another timeout, matcher or `statusMessage`) shows as `[!] Skills Sync · modified` and needs the same review again. The tool reads that record the way Codex does: the key is the exact string `<hooks.json path>:session_start:<group>:<handler>`, the path under `CODEX_HOME` canonicalized when `CODEX_HOME` is set and `~/.codex` as written when it is not, and the hash is Codex's own (sha256 over the entry normalized as Codex normalizes it). It reports one of three states: trusted, new (no record for the key: every sync prints the trust step as a note), or changed (a record with another hash: every sync prints the review-again step as a note). The trust stays your tap: the tool never writes `config.toml`, not even the new hash of an entry it wrote. Claude Code asks nothing.

`hook` is what the entry runs. It syncs, printing only what changed (the report sync would print) and any conflict (on stderr); then it tends every git repository it can see, whoever owns it and wherever its `origin` points (it replaces the old `sync-dev.sh`, which did this for one repository on one machine). Those are the repository the session started in (its main checkout when the session started in a linked worktree, such as a task's `<repo>/.claude/worktrees/<name>`, found with `git rev-parse --git-common-dir`) and every git repository directly beside it, in the same parent folder; a session that starts outside any repository takes the git repositories directly inside its folder instead. One level only, never deeper; a folder whose `.git` is a file (a linked worktree, a submodule) or whose name starts with a dot is none. They are found again on every run (nothing is remembered) and tended six at a time. For each:

- `git status` is read first (`--no-optional-locks`); one it cannot read is named on stderr (`<path>: git status not read (exit 128): …; left alone`) and never taken for clean.
- A repository with no `dev` branch (neither its own nor `origin`'s) or no `origin` takes no part in the dev flow: it is not mentioned and not touched.
- One on `dev` with a clean tree is fetched (every branch of `origin`, gone ones pruned; cut off after 15 s, with every process the fetch started, so a hung network cannot stall the session start) and fast-forwarded to `origin/dev` with `merge --ff-only` (`<path>: dev fast-forwarded to <sha>` when it moved). `--prune` removes only remote-tracking refs (`origin/<branch>`) whose branch is gone from `origin`, never a local branch. The merge runs the repository's own `post-merge` hook, as `git pull` would. Just before the merge the branch and the tree are read again: one switched or edited while the fetch ran is left alone (`<path>: changed while origin was fetched; left alone`). A failed or cut-off fetch (`<path>: fetch of origin failed (timed out after 15 s), …`), an `origin` with no `dev` (`<path>: origin has no dev; left alone`) or a `dev` that cannot fast-forward is one stderr line, and the checkout is left as it was.
- One that is dirty or on another branch is named on stderr (`<path>: on feat/x, dirty (2 files); left alone`) and not touched, not even fetched.

Nothing is ever rebased, reset or switched, and `main` is never touched. The lines come out in the order the repositories were found: the session's own first, then the others by name. 90 s after the hook started no fetch begins and nothing more is asked of GitHub: the repositories still waiting are left as they are, counted in one stderr line (`3 repositories not fetched: out of time (90 s since the hook started)`). With at most one 15 s fetch in flight per slot and only local git calls after it, the hook ends inside the 120 s its entry allows.

Last, for the session's own repository only (not the ones beside it, and none when the session started outside any repository), one line says what is not in dev yet: `oneezy/skills: 2 branches ahead of dev (feat/a, feat/b), 1 open pull request (#12)`. The branches are counted in the checkout from the refs the fetch brought (one `git for-each-ref --no-merged`); for an `origin` on GitHub the pull requests are one GitHub request, given up at the deadline. Only the session's repository costs a request, because the hook often runs without a token and anonymous GitHub allows 60 requests an hour, which the sync's own release read needs. Without a token, a 401, 403 or 404 for the pull requests (what GitHub answers anyone about a private repository) is not reported, and the line carries the branches only; with a token it is one stderr line. A repository elsewhere is named by its path and gets the branch count only. Nothing is printed when nothing changed and nothing is waiting; the harness feeds stdout to the model, so stdout carries only what you would read. Exit 0 unless the sync hit a conflict; GitHub out of reach, a failed fetch or a checkout that cannot fast-forward are stderr lines, not a failed hook; a failed git call is named with how it ended and git's own words (`fetch of origin failed (exit 128): fatal: …`).

## Status

`status` is the one answer to "is this machine done". It needs no library on the machine. It reads the latest release of `oneezy/skills` from GitHub (`--library owner/repo` for another release repo; `GITHUB_TOKEN` or `GH_TOKEN` is sent when set, the base URL comes from `SKILLS_SYNC_GITHUB_API` so tests point it at a fake) and probes this machine, writing nothing: the account plugins claude.ai synced into Claude Code (`<id>@synced`), the plugins installed through each harness's CLI (from the library's catalog `oneezy-skills`, or from anywhere else), the loose links in each user folder (`~/.claude/skills`, `~/.agents/skills`, Codex's old `~/.codex/skills`) and the real skill folders there, the session hook entry in each user hooks file, the managed block in each global instructions file, and the checkouts of `oneezy/skills` and `oneezy/tools` among the repositories [the hook](#the-session-hook) tends (the repository the current folder is in, or its main worktree from a linked one, and the git repositories beside it; outside any repository, the ones directly inside the current folder). The hook tends every repository; `status` judges only these two. Per detected harness it prints its form (Claude Code: account plugins; Codex and Hermes: plugins from GitHub), one line per library plugin against the release, one line per skill name listed in more than one place, the hook line and the block line; then the checkouts, then the manual steps. Hermes's plugins are read from its own files (`<hermes home>/plugins/<id>/plugin.json`, the install rows in `plugins/.install-metadata.json`, the lists in `config.yaml`), so `status` never runs `hermes`; a plugin hermes recorded from `github.com/<owner>/<repo>` shows as `<id>@<owner>-<repo>`, so the library's are `<id>@oneezy-skills` here too:

```
latest: oneezy/skills release-17 (ae92a54)
Claude Code  form: account plugins
! matt-pocock@synced 1.3.0 (latest 1.3.1); start a new Claude Code session
= oneezy@synced 0.43.1 (latest 0.43.1)
! oneezy-status listed twice: oneezy@synced, loose link -> /root/.skills-sync/skills/oneezy/oneezy-status

! global block in /home/justin/.claude/CLAUDE.md is stale (release-25 SHARED.md text; this tool writes the pointer to /oneezy-agents); run sync

. 5 other plugins left alone: data@synced (anthropic-plugin-directory), ...
Codex  form: plugins from GitHub
! no plugins installed (latest release-17)
! no session hook entry in /home/justin/.codex/hooks.json; run sync
= global block in /home/justin/.codex/AGENTS.md current
Checkouts
= /home/justin/dev/skills on dev, clean
! /home/justin/dev/tools on feat/x, dirty (2 files); commit or stash them, then switch it to dev

   1. Open https://claude.ai/customize/plugins (Customize > Plugins) in a browser, signed in to the claude.ai account Claude Code uses.
   2. Find play and switch it on.
   3. Start a new Claude Code session so claude.ai syncs it in, then run npx --yes @oneezy/skills-sync@latest status: each should show as <id>@synced.

```

`=` is green, `!` red, `.` a note. Under each harness: the plugin lines sorted by id, then the duplicate lines, then the hook line, the block line and one red line per block an older version left in a repository file (`skills-sync block (brain) in <file>; remove it by hand, …`), then the notes (what else is in the user folders, which other plugins are left alone). A plugin switched off, at claude.ai or through the CLI, loads nothing: it is listed, never judged, and its skills count for no duplicate. When Codex cannot render its prompt input, an installed plugin's skills are not read (`skills not read`) and its version alone is judged. A Codex plugin's user-only skills, which its prompt input never shows, are read from the copy Codex runs, so they are no `missing` line.

Red, and exit 1: a plugin behind the release (its version, or its skill set; the line says what brings it up: `run sync`, or for an account plugin a new Claude Code session); a plugin the tool installed on Claude Code (the account plugin of the same name is the form there, and a CLI install hides it); nothing of the library installed on a plugin harness, or Codex's plugins not read because `codex` is missing or cannot list them (`! plugins not read (no codex on PATH; latest release-17)`, never `no plugins installed`: the machine cannot know that); a duplicate skill name; the release not readable; no session hook entry, or the old `sync-dev.sh` entry still beside it, or a hooks file that cannot be edited; the global block missing, stale (another text than this tool's pointer, or an older block such as `brain`), hand-edited (its text no longer hashes to its stamp; sync restores it after a backup) or unwritable; a block in a repository file; a checkout that is dirty or not on `dev` (the line says to commit or stash, or to switch it to `dev`), or whose `git status` could not be read (`! <path>: git status not read (exit 128): …`, never counted clean). A plugin ahead of the release (Codex's marketplace snapshot is `main`, which runs ahead until the release job finishes; claude.ai may deliver ahead too) is a note: sync leaves it as it is. A Codex hook entry says how Codex sees it: `trusted in Codex`, `new in Codex, not trusted yet` or `changed since Codex trusted it, review again`; the last two are a green line and a manual step, not a red line: the machine is right, the trust is yours. No checkout in reach is one note. What an older version left (`~/.skills-sync`, its answers file) and a harness the release's settings do not serve are notes above the harnesses (outside the cloud; there the old clone is the `cloud-setup` step's evidence).

A **manual step** is something only you can do, so it never makes the exit code non-zero on its own and never hides a red line: the red lines print first, the steps after, each a numbered block with numbered steps you can follow on a phone, and the summary counts both (`status: 2 red lines, 1 manual step`; `status: all green` only when there is neither). The steps, each with a stable `id` in `--json`: `claude-plugins` (a release plugin the claude.ai account does not deliver, or one switched off there: the Plugins page and what to toggle), `claude-account` (`claude` lists no account plugin at all: the sign-in and `syncClaudeAiPlugins`), `codex-trust` (the hook trust in Codex's TUI, once per machine or WSL distro, and again after the entry changed: the `· new` or the `· modified` row), `codex-other-plugins` (a plugin of a library plugin's name from another marketplace that is not the ChatGPT account's own: uninstall it by hand), `adopt-or-delete` (what sync leaves in Codex's skills folders because it is not the library's: a folder that is not exactly the release's files for the skill, a link to somewhere that is not a library copy, a library copy or dangling link no plugin carries; the library's own copies are not listed, sync removes them), `chatgpt-update` (a release plugin behind or missing on the ChatGPT account: the line to type in ChatGPT; see [ChatGPT](#chatgpt)), and in the cloud `cloud-setup` (the old setup line ran in this session: `~/.skills-sync` exists or `~/.claude/skills` holds loose links; it came from the environment's setup script or from an agent that followed a repository's "run this first" line, so the step says to check the setup script and replace the old line wherever it is with `npx --yes @oneezy/skills-sync@latest --quiet`). `--quiet` prints only the red lines, the manual steps and the summary, and nothing at all on a done machine.

The block line compares the block's stamp with this tool's text, with or without the release: `current`; `is stale (release-25 SHARED.md text; this tool writes the pointer to /oneezy-agents)` (or `built-in text` for an older tool's); `is hand-edited (its text no longer matches its built-in stamp)`. `--json` keeps `unknown` among the block's statuses for older readers; it is no longer given. The line says "stale" where `--json` says `outdated`: the key keeps the value earlier versions printed.

### ChatGPT

ChatGPT keeps the plugins on Justin's account, and only Plugin Creator inside a ChatGPT chat changes them, so no command here writes them. A Codex signed in with ChatGPT lists the account's own plugins as the remote marketplaces `created-by-me-remote` and `workspace-*`, versions included, so `status` reads them there (`codex login status`, then the listing it already has): after the harnesses, a `ChatGPT  account copies, read through Codex` section with one line per release plugin, green at the release, a note pointing at the `chatgpt-update` manual step when a copy is behind or missing. The step says to type `@oneezy-skills update my ChatGPT plugins to the latest oneezy/skills release` in ChatGPT, which runs `/oneezy-skills`'s procedure there (oneezy/skills `skills/oneezy/oneezy-skills/references/chatgpt-update.md`); while the account's oneezy copy is older than 0.46.0 (the first with that procedure) or missing, it first gives a Plugin Creator line that brings oneezy up, then that one in a new chat. Each copy is judged by its own skills: Codex prints both copies' skills under the plugin's name, and their `(file: …)` paths, under `plugins/cache/<marketplace>/<id>/`, tell them apart. Codex lists the account's plugins whether or not they are installed in this Codex (`"installed": false` in `codex plugin list --json` for one only on the account), and each counts as the account's copy; one installed here also loads in Codex, the rest do not. A Codex signed in with ChatGPT that lists no account plugin at all has not read the account yet, so that is a `not checked` note too, never "not on the ChatGPT account". A Codex not signed in with ChatGPT is one note (`not checked: …`); a machine without Codex, a Codex that cannot list its plugins, and a cloud session show no section (`--json` still gives the reason). Only `status` asks `codex login status`; `sync` and the hook do not. `--json` carries the same as `chatgpt` (`checked`, `reason`, `plugins` (each `id`, `marketplace`, `version`, `latest`, `current`, `ahead`, `differ`), `current`, `lines`). The account's copies are left out of the Codex section's `other plugins left alone` note (`plugins.other` in `--json` keeps them). Codex loads both copies of each plugin, the library's and the account's, so a skill doubled only by the account's copy of the same plugin is a note, not red. Nothing here is ever red: ChatGPT is Justin's account, not the machine.

In a cloud session (`CLAUDE_CODE_REMOTE=true`) the account plugins arrive on their own and no hook or checkout exists, so `status` shows the block lines and the manual steps only, reads the release for the block's text alone (there is no release line, and GitHub out of reach makes the block line a note, not red), and the exit code follows the block lines.

`--json` carries the same facts under stable keys (added, never renamed): `release` (`repo`, `tag`, `number`, `commit`, `tool`), `cloud`, `oldLibrary` (`path`, `kind`, `target`), `oldLocalFile`, `lines`, `checkouts` (`path`, `repo`, `branch`, `dirty` (`null` when git could not say), `clean`, `ok`, and `error` only when git could not be read), `manualSteps` (`id`, `title`, `steps`), `chatgpt` (see [ChatGPT](#chatgpt); `null` in the cloud), `red`, `ok`, and per harness `name`, `form`, `cli`, `plugins.synced` / `plugins.installed` (each with `version`, `latest`, `current`, `skills`) / `plugins.other`, `loose`, `folders`, `duplicates`, `hook` (`file`, `present`, `current`, `trusted`, `trust` (Codex: `trusted`, `new` or `changed`, and `trusted` is true only for the first; `null` on Claude Code, and on Codex when the hooks file cannot be read); `null` for a harness without a hooks file), `block` (`file`, `present`, `current`, `status` (`current`, `missing`, `outdated` (the line says stale; the value is the one earlier versions printed), `conflict`, and from 0.12 `hand-edited` and `unknown` (the latest text not read)), `ids`, `stamp` and `latest` (each `release` and `sha256`, or `null`); `null` for a harness without a global file), `repoBlocks`, `lines`. `/oneezy-status` reads it.

## Branches

`branches [owner/repo ...]` applies the branch rules (ADR-0013 in `oneezy/skills`) through GitHub REST, with the token from `GITHUB_TOKEN` or `GH_TOKEN`, to each repository named; with none, to every repository the token's user owns (archived ones left out; without a token that is exit 2). It needs no library on the machine. Per branch, in name order:

- `main`, `dev`, the repository's default branch, any branch whose name ends in `-keep`, and any `research/` or `prototype/` branch are kept: never deleted, never the target of a request, merged or not. The names are exact: `Main`, `-Keep` or `Research/x` are other branches.
- A branch that is the head or the base of an open pull request is left alone (deleting it would close or retarget the pull request; pull requests are never touched).
- A branch whose pull request was merged into `dev` is deleted, and so is one whose commits are all in `dev` (compare `dev...<branch>` ahead by 0), whether or not a pull request was closed without merging first.
- A branch whose pull request was closed without merging gets the tag `archive/<name>` at its head, then is deleted. A tag of that name already at the head is reused; one at another commit is a problem line and the branch stays.
- Every other branch is left alone and listed with why: protected on GitHub, merged into `dev` but with commits after the merge, merged into another branch, or no pull request and commits `dev` lacks.

Right before its first tag or delete, a branch's head is read once more; one pushed to since the listing is left (`moved during the run`). A repository without a `dev` branch is skipped as a note. One the token cannot read (404) or write (403 on the first tag or delete) is skipped with a problem line; the others still run. `--plan` lists every tag and delete without making a single write request:

```
oneezy/tools
- feat/146-status-against-release  delete: pull request #160 merged into dev
- feat/old-idea  tag archive/feat/old-idea at 1a2b3c4, delete: pull request #12 closed without merging
. feat/next  left: open pull request #170
= kept: dev, main, prototype/ui, research/agent-standards, spike-keep
plan: 2 to delete, 1 to tag, 1 left alone, 5 kept
```

Exit 0 when every change was made (or planned), 1 when anything was reported (a skipped repository, a tag in the way), 2 for bad usage. `--quiet` prints only the changes and the problems. `--json` carries the same under stable keys: `plan`, `ok`, and per repository `repo`, `kept`, `deleted` (`branch`, `reason`), `archived` (`branch`, `tag`, `commit`, `reused`), `left` (`branch`, `why`), `skipped`, `problems`, `lines`.

A scheduled workflow in `oneezy/tools`, `.github/workflows/branches.yml`, runs `branches` once a day (10:17 UTC) with the latest published tool and the `PROJECT_PAT` secret as `GITHUB_TOKEN`, over every repository that token's user owns. The schedule is a plan until the repository variable `BRANCHES_APPLY` is `true` (set once the first plan has been read; unset it to go back to plans). Its token check comes first: each repository the run will touch is named with whether the token can write it (`skipped: cannot write <repo>` for one it cannot, which is never attempted; the run ends red so it is seen), and `layerdbiz/*` is refused by name (outside the token's reach, ADR-0013); the command then runs on the ones that passed, and the run's step summary carries a table per repository with every line under it. A run by hand is a plan unless told otherwise: `gh workflow run branches.yml -f plan=true` (from a cloud session, `gh api repos/oneezy/tools/actions/workflows/branches.yml/dispatches -f ref=main -f 'inputs[plan]=true'`) lists what a real run would do without a write, `-f plan=false` applies at once whatever the variable says, and `-f repos='oneezy/skills oneezy/tools'` limits a run to named repositories. Dispatch and schedule exist only once the workflow file is on `main`. A branch to hold gets the `-keep` suffix (rename it on GitHub) before the next 10:17 UTC; `main`, `dev`, `-keep`, `research/` and `prototype/` branches are never named in a request, by the schedule or by hand.

## Artifacts

ChatGPT's plugins are now brought up inside ChatGPT by the line above and verified by `status` through Codex (oneezy/skills ADR-0015); what follows is the older upload path, kept for a manual upload. **`build --artifacts`** writes what that upload needs into `artifacts/` (generated, gitignored, never part of a check):

```
artifacts/
  <id>-<version>.zip     one archive per built plugin, holding the package under one folder named <id>
  releases.json          per plugin: archive, sha256, version, commit, files, release
  <id>.changes.md        only when the recorded release holds a file the new archive lacks
```

The archive is the package `build --plugins` writes, at the version its manifests carry, so `--artifacts` alone archives the packages as they are on disk when they are as built, and what a build would write when they are not; it writes no package and no catalog itself. The ZIP is written by the tool with no dependency and is **deterministic**: every entry stored (no compression), entries sorted by path, forward slashes, no directory entries, one fixed timestamp (1980-01-01 00:00), no symlinks (a link inside a skill folder is never followed: it is left out, with a report line). Two builds of the same input give identical bytes on any machine and in any checkout, a CRLF one included (a package holds LF, see [Plugins and catalogs](#plugins-and-catalogs)), so the sha256 says whether a plugin changed: a library commit that touches no input of a package leaves its archive's name and bytes as they were, and editing one skill changes only its plugin's archive. An older archive of a plugin, an archive for an id no longer in the config and a note that no longer applies are removed; any other file in `artifacts/` is left alone, and so is the archive of a plugin that could not be built this run.

`releases.json` says, per plugin: `archive` (its path in the library), `sha256`, `version`, `commit` (the upstream commit for a source plugin, the library commit the package was built at for an own group, null without git), `files` (the archive's entries) and `release`, the last upload the config records for it, or null.

The config's optional `releases` section is that record (legacy: since ADR-0015 nothing writes it, and `status` reads the account through Codex instead), one entry per plugin id written by hand after each upload: `plugin_id`, `release_id`, `sha256` of the archive, `scope` (`personal` or `workspace`), `date`, and optionally `files`, the archive's entries as `releases.json` lists them; the schema admits nothing else there. An archive whose sha256 equals the recorded one has not changed since its upload. A ChatGPT plugin update overlays files; omissions remain unless the current supported API receives explicit `delete_paths`. When recorded `files` are missing from a new archive, `artifacts/<id>.changes.md` lists them for review. An authorized deletion uses only verified exact plugin-root-relative paths, the current source’s `expected_release_id` and readback. The note never authorizes deletion or automatic replacement/uninstall. An API without deletion support is reported as blocked. A recorded path counts with or without its leading `<id>/` folder. No recorded `files`, or every one still in the archive: no note.

## Check

**`check`** answers one question: is what is committed consistent? It reads the library and nothing else (no network, no clone, nothing written, no harness folder), prints one line per problem as `<path>: <reason>`, and exits 1 when there is any; a clean library gets one summary line and exit 0. Run it before committing; CI runs it on every push. It is a command, never a git hook. `--json` gives `problems` as `path` and `reason` pairs, and `notes` the same way for what was passed over without failing (a declared group with no skill yet, printed as `note: <path>: <reason>`); `--quiet` says nothing when the library is clean.

1. **Frontmatter of every own skill** (`skills/<name>/SKILL.md` and `skills/<group>/<name>/SKILL.md`): `name` is the folder's name and a valid skill id (lowercase letters, digits and single hyphens, at most 64 characters), and `description` is present. A skill folder under `skills/play/` is named `play-<name>`; one that is not fails as `skills/play/unslop: a skill in the play group is named play-<name>; rename the folder (and its frontmatter name) to play-unslop`. Third-party skills are upstream's and are not checked. A second own skill of a name already taken (`skills/trident/x` beside `skills/oneezy/x`: the first by path wins) and a `SKILL.md` deeper than `skills/<group>/<name>/` are problems too, with the folder and why; nothing else reports them, and a plugin built from the group would carry the wrong one.
2. **Every `flow.yaml` beside an own `SKILL.md`**, against `schemas/flow.schema.json` and the rules a schema cannot say:

   | key | rule |
   |---|---|
   | `skill` | required; the folder's name |
   | `purpose` | required text |
   | `runtime` | a list of tools and connections |
   | `refs[]` | `token`, `kind` (`skill`, `plugin`, `app`, `file`, `url`), `id`, `need` (`required`, `optional`, `conditional`, `example`, `mention`), optional `when` |
   | `unresolved[]` | `token` and `note` |
   | `agents.max` | an integer, 0 or more |
   | `steps[]` | required, at least one; each has a unique `id` (lowercase letters, digits, hyphens) |
   | step `after` | one step id or a list of them, each naming a step of this flow |
   | step `parallel`, `join` | `parallel` lists at least two member ids and needs `join`, the id where they meet; all name steps of this flow |
   | step `loop` | `until` required, `every` optional |
   | step `outcome` | only the keys `done`, `fail`, `input` |
   | step `does`, `if`, `returns`, `needs[]`, `calls` | free text; `needs` a list; `calls` names a `skill`, `plugin` or `app` |

   Any other key is refused, so a typo is caught. A problem reads `skills/oneezy/x/flow.yaml: $.steps[2].after: no step has the id open-pr`.
3. **Forbidden terms** left in a package file after its source's `adapt` rules, one problem per line and term, and a note for every rule that matches nothing (see [Adapting a source](#third-party-sources)).
4. **Generated-file drift.** The plugin form, by the same computation as `build --check`: every file a build would write or remove, and every package it cannot build (nothing when `generate.plugins` is false). And `skills-sync.lock.json`, against the lock a `refresh` would write from the snapshots under `upstream/` as they are: an entry edited by hand, an entry no source selects, a snapshot changed since; differences are named `source` (its version, commit or date) and `source:skill`. A config library that still has only the 0.4.0 `skills-lock.json` gets one problem, `old lock format; refresh migrates it`. A source `skills-sync.json` holds at a version the lock does not have it at (the hold was landed, the update was not run) gets one problem on `skills-sync.json`, `sources.<id>.version holds 1.2.0 but the lock has 1.3.1; run update <id>`. A library without snapshots (a clone before its first `refresh`) has nothing to compare the lock with, so CI runs `refresh --frozen` first. `artifacts/` is never drift. A `skills-sync.json` the schema refuses is reported rule by rule and nothing is computed from it. The summary line names the command that writes what drifted (`build --plugins --catalogs`, `refresh`).

A library without a config has no generated files to check; its frontmatter and flows still are.

## Rules it never breaks

- A machine command keeps nothing of its own on the machine: no clone, no `~/.skills-sync`, no `skills-sync.local.json`, no cache, nothing remembered between runs. What an older version left is named, never read, never touched.
- A machine command never looks for a library on the machine: `--repo`, `$SKILLS_REPO` and a checkout above the current folder matter to the library commands only, and none of them clones one.
- A machine command removes a loose link only when it points into a library checkout or clone, at `~/.skills-sync`, or at nothing; a link pointing elsewhere and a real folder are named and left alone. A library command creates or retargets a link only when its target is inside the library.
- `build` applies a source's `adapt` rules only to the Markdown and text files it copies into a package: never to a script, the snapshot, the working set or the lock, and with no model or network.
- `build` writes only `plugins/<id>/`, its Hermes rendering `dist/hermes/<id>/` where the library opts in, and the two catalogs, inside the library, plus `artifacts/` when `--artifacts` asks; `build --check` and `check` write nothing at all. A package is rewritten only when its inputs changed. `build` never follows a link: one inside `plugins/<id>` or `dist/hermes/<id>` is a conflict and the package is left alone.
- `check` never touches the network and never clones a library to have one to check.
- `synced/` (Claude's account skills) and `.system/` are never touched.
- Third-party copies in `.agents/skills` are written only by `refresh` (config library; `remove` deletes a removed source's) or by `npx skills` (legacy library).
- `refresh`, `add` and `remove` touch nothing outside the library: no pull, no `~/.skills-sync`, no harness folder.
- `refresh --frozen` never writes the lock and never moves a source upstream; only an explicit `update` (or `refresh`) does, and only the sources it names.
- `update` never writes `skills-sync.json`; a hold is a config change the caller lands.
- No settings file of any harness is ever edited by the tool. A plugin is installed, reinstalled or removed only through the harness's own command, and removed only when it came from the library's catalog; a skill's loose link goes only after its plugin is verified on that harness.

## Commands and flags

Nothing prompts. A machine command takes three flags and `--library` (`hook` only `--library`: the hook entry runs it bare, and any other flag is exit 2); a library command keeps every flag it had:

```
sync (default), status, unlink:  --plan  --quiet  --json  --library owner/repo
hook:                            --library owner/repo
branches [owner/repo ...]:       --plan  --quiet  --json
update | refresh: [<source>...]  --to <version>|previous|latest  --frozen  --retry  --json
versions <source>: --json
add <source>: --id <id>  --root <path>  --skills a,b | --skills '*'  --as old=new,...  --plugin <id> | --no-plugin
remove <source>: --plan  --json  --quiet
build: --plugins  --catalogs  --artifacts  --check
check: --json  --quiet
develop setup [<plugin>...] | status | remove: --repo <library>  --root <project>  --plan  --json  --quiet
every library command: --repo <path>  --symlinks | --junctions  --expect-revision <sha>  --remote-ref <ref>
migrate-aliases, rollback-aliases: --alias-file <json>  --receipt <path>
```

Commands: `sync` (default; see [What a run does](#what-a-run-does)), `status` (this machine against the latest release, see [Status](#status)), `hook` (what the session hook entry runs, see [The session hook](#the-session-hook)), `branches` (the branch rules on GitHub, see [Branches](#branches)), `unlink` (see [unlink](#unlink)), `update` (alias `refresh`), `versions <source>`, `add <source>` and `remove <source>` (see [Third-party sources](#third-party-sources)), `build` (see [Plugins and catalogs](#plugins-and-catalogs) and [Artifacts](#artifacts)), `check` (see [Check](#check)), `develop` (development links, builds and Development projects: `packages/skills/DEVELOPMENT.md`, decisions in `docs/adr`), `migrate-aliases` and `rollback-aliases` (above). `projects` is retired (ADR-0007: nothing links skills into projects any more; every harness reads its own plugins or user folder): one line, exit 2. `adopt-brain` and `rollback-brain` are retired (the global block points at `/oneezy-agents`, `/oneezy-brain` owns Brain routing): one line, exit 2.

A flag that is not a machine command's own (`-y`, `--yes`, `--ask`, `--agents <ids>`, `--global`, `--no-global`, `--projects <names>`, `--no-projects`, `--dev <dir>`, `--copy`, `--wsl <distros>`, `--no-wsl`, `--pull`, `--no-pull`, `--no-restore`, `--retry`, `--sidecars`, `--no-layers`, `--links`, `--plugins`, `--no-remember`, `--no-entrypoints`, `--adoption-file <json>`, `--watch`, `--repo <path>`, `--symlinks`, `--junctions` and the other library flags) is accepted, does nothing, and is named in exactly one line on stderr (`hook` excepted: it refuses any flag but `--library`, exit 2). An option the tool never had is `unknown option`, exit 2, with the help; so is an unknown command.

## Development

```
pnpm install && pnpm build
pnpm test          # tsc, then vp test (Vitest) on temp folders and temp git repos standing in for upstream; symlinks where the machine allows them, junctions otherwise
node dist/src/cli.js --plan                      # the machine sync against the real release, writing nothing
node dist/src/cli.js check --repo <library>      # a library command on a checkout
```

`test/fixtures/tls/key.pem` (with `cert.pem`) is a self-signed key made for the proxy tests alone, valid for 127.0.0.1; it secures nothing.

Publishing is not done by hand. Bump `version` here (and `VERSION` in `src/version.ts`), merge to `dev`, promote to `main`: `.github/workflows/publish-skills-sync.yml` publishes any version npm does not have yet, through npm trusted publishing (no token, no `npm login`, no 2FA prompt), with provenance. To retry, run that workflow from the Actions tab.

The three JSON Schemas under `schemas/` ship with the package: `skills-sync.schema.json` for the config (sources, plugins, the `generate` switches, the `renderings` opt-in, the `releases` upload record), which `refresh`, `add`, `build` and `check` validate before doing anything; `skills-sync.local.schema.json` for a checkout's `skills-sync.local.json` (the library commands read its `unavailable` and `links` keys; older versions kept this machine's answers in it), validated on every read; and `flow.schema.json` for an own skill's `flow.yaml`, which `check` validates. The validator and the ZIP writer are in the tool; there is no dependency for either.
