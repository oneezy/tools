# Update the ChatGPT plugins

Runs inside ChatGPT (the website or the desktop app) when Justin types:

```
@oneezy-skills update my ChatGPT plugins to the latest oneezy/skills release
```

That line is his authorization for every write below on his **personal** plugins: updating each library plugin's copy to the release's files, deleting the files the release dropped, and creating a library plugin the account lacks (ADR-0015). Workspace plugins and every plugin that is not the library's stay as they are. This branch replaces the sync script and `status --json`: ChatGPT has neither, and the report in step 7 is the end of the run.

1. **Precondition.** Read `references/capabilities/chatgpt.md`, load the actual Plugin Creator (`update-plugin`, `create-plugin`) and Plugin Management instructions, and discover their tools. Done when listing personal plugins, reading a plugin's files and updating a plugin are all exposed; otherwise stop and name the missing tool, and tell Justin to type the line in a ChatGPT chat that has Plugin Creator.
2. **Read the release.** Fetch `https://api.github.com/repos/oneezy/skills/releases/latest` (public: web fetch, code execution or the GitHub connector) and keep its `tag_name`. Download the `release.json` asset from its `browser_download_url`; for each key of its `plugins` object (the plugin id) keep `version` (null is "unversioned"), `archive`, the archive asset's `browser_download_url`, and `files` (path inside the plugin, no `<id>/` prefix, to sha256). When the asset cannot be downloaded, read the same facts through the GitHub connector at the tag: the plugin ids from `.agents/plugins/marketplace.json`, the files under `plugins/<id>/` and their content (hash each one with code execution), and the version in `plugins/<id>/.codex-plugin/plugin.json`. Done when every plugin id has its version and its file map.
3. **Find each copy.** List Justin's personal plugins. A copy is the plugin whose manifest `name` is the release plugin id; keep its backend plugin id, its current release id, its version and its file map (paths relative to the plugin's root; hash each file when the API gives no digest). Done when every release plugin is **found** (exactly one copy), **missing** (no copy by manifest name and none by display name), or **ambiguous** (more than one candidate, or a display-name match whose manifest name differs).
4. **Diff each found copy.** The manifests (`plugin.json`, `.codex-plugin/plugin.json`, `.claude-plugin/plugin.json`) are compared with their `version` field left out, since the updater may bump it on its own; a version that differs is a **version drift**, reported, never a change. *Changed* are the release's paths whose sha256 differs or that the copy lacks; *removed* are the copy's paths the release lacks. **Stop rule:** when the copy and the release share fewer than half their paths, or a manifest would be removed, the paths are misread: mark that plugin `failed: paths do not line up` with both lists and delete nothing. Done when each found copy is **up to date** (both lists empty), has both exact lists, or has failed the stop rule.
5. **Bring each plugin up**, in `release.json` order:
   - **Bytes.** Download the plugin's archive and check its sha256 against `release.json`; or, without downloads, read the needed files through the GitHub connector at the tag (`plugins/<id>/<path>`: the changed ones for an update, every one for a create) and check each sha256. An archive keeps the single `<id>/` root folder the release's archives have.
   - **Found, not up to date:** update the copy by its backend id, with `expected_release_id` set to the release id from step 3, the changed files (or the whole archive, when that is what the API takes), and `delete_paths` set to the removed paths, each relative to the plugin's root. Keep the release's version in the manifest; a version the updater bumps on its own is reported, not undone.
   - **Missing:** create it from the archive, personal scope.
   - **Ambiguous:** write nothing; report the candidates.
   - **Release changed** (the expected release id no longer matches): redo steps 3 and 4 for that plugin and try once more; a second mismatch is `failed: release changed during update`.

   Done when every plugin step 5 wrote has the release id the API returned, or a failure in the API's own words.
6. **Read back** every plugin step 5 wrote. Done when each one's file map equals the release's, manifests compared as in step 4; any difference marks it `failed: readback differs` with the paths.
7. **Report**, one line per release plugin: `updated <old> → <new>` (third-party plugins can change files without a new version, so `1.3.1 → 1.3.1` is normal), `created <version>`, `up to date`, `ambiguous: <candidates>`, or `failed: <reason>`, with `(version drift: <copy's> vs <release's>)` added when step 4 found one. Then print: "A new chat loads the new skills; `@oneezy-status` there is a quick check. On the PC, `npx @oneezy/skills-sync status` shows ChatGPT current once Codex there next starts." Done when every release plugin has a line.
