One library, `oneezy/skills`, holds authored skills and locked upstream snapshots. This skill runs the published tool through the script beside it and ends every run with the manual steps still open. It is the wrapper for every skill or plugin request Justin makes in any harness (sync, update, add, remove, change): the library changes first and each harness follows from its release, so the harness's own installer (`/plugin`, Codex's skill-installer, ChatGPT's Plugin Management, Hermes's skills hub) runs only where a step below calls it. Preserve pins, invocation boundaries, unrelated instructions and dirty work.

The tool has two kinds of command (ADR-0014). **Machine commands** act on the machine they run on and need no checkout: `sync` (the default), `status`, `hook`, `branches`, `unlink`, with `--plan`, `--json`, `--quiet` and `--library owner/repo`. They read the latest release of `oneezy/skills` on GitHub; nothing is cloned, remembered or asked (ADR-0012), and an older flag is ignored with one line on stderr. **Library commands** change the library: `update`, `add`, `remove`, `versions`. Each harness gets one form (ADR-0007): Claude Code the claude.ai account plugins, Codex and Hermes plugins from GitHub.

1. Read `references/requests.md` and map the request. Inside ChatGPT, where no script runs, the request takes the ChatGPT rows of that table in place of steps 2 to 6. A machine command runs through the script directly. Change/add/playground reads `references/changes.md` before editing a fresh clone. Sync installs the latest release; `update` moves a source, asked for here or by the library's daily run.
2. For a global block audit, a development build of the tool or a desktop handoff, read `references/global-block.md`. For explicitly approved historical Skills/Status alias cleanup, read `references/aliases.md`. Inspect existing rollout work first. Hold a review/no-publication request on a review branch; do not automatically land or release it.
3. Run `scripts/sync.ps1` on Windows (`pwsh -File <skill-folder>/scripts/sync.ps1 [args]`) or `scripts/sync.sh` elsewhere (`bash <skill-folder>/scripts/sync.sh [args]`). Scripts run the latest published tool (ADR-0008); `SKILLS_SYNC_CLI` selects a reviewed local build. Require Node 20+ and npx; git only for the library commands. No args is a quiet sync. Where oneezy/skills cannot be cloned or pushed (a cloud thread), `update`, `add`, `remove` and `versions` run in the library's own workflow instead: `gh api repos/oneezy/skills/actions/workflows/run.yml/dispatches -f ref=dev -f 'inputs[command]=update' -f 'inputs[args]=matt-pocock'`, then watch the run and the `land/*` branch it pushes (`references/changes.md`, Dispatch).
4. For authored Oneezy instructions or capability changes, load Matt’s actual `writing-for-agents` skill and its examples through this host’s catalog and adapter. Inventory first, retain business rules and dependency/approval boundaries, shorten each `SKILL.md` with explicit reference branches. Unslop must not undo that structure. Do not edit upstream Matt or PStack. In a source checkout run `node scripts/oneezy-capabilities.mjs --write`, then its tests, before canonical build/check; this bundles the maintained repo contract/catalog.
5. Finish with the manual steps. Run the script with `status --json` (read-only, also after a failed run), then read `references/report.md` and invoke `/oneezy-status` in Skills Sync mode with that output and the canonical command output. A normal landed change links the new release (a plain sync) then loads `/oneezy-migrate` with the update report; a held development artifact reports its tests and handoff instead.
6. End the message with the open manual steps from `status --json`: each `manualSteps` entry as its `title`, then its `steps` numbered, in the tool's words, in the tool's order. `manualSteps: []` ends with "No manual steps open." When `status --json` has no `manualSteps` key, the tool is older than 0.9.0: say `Skills Sync <version from --help> cannot list manual steps yet; done cannot be judged`, never write "No manual steps open.", and do not run `branches` or `hook` (0.9.0 commands). The steps are Justin's: list them and never perform one (no `codex plugin remove`, no folder or link deletion, no settings or setup-script edit) unless he asks for that exact step in this conversation. This list is the last thing Justin reads; never summarise it away, and never mark the run done while a step is open or `ok` is false.

Before calling a dependency, read `references/capabilities/contract.md`, then the adapter for this host. Load its actual instructions and discover its tools; a name or mention does not execute it.

For a requested authoring, packaging, plugin install/connect/update or delivery audit, read `references/management.md`. Load the actual creator/management skill for the selected host and perform its supported action within scope; verify the result. Plugins reach a machine through each harness's own route (claude.ai account plugins, `codex plugin`, `hermes plugins`); `unlink` takes the tool's own work away again.

The tool writes exactly three things on a machine: the skills block in the global instructions file of Claude Code and Codex (ADR-0011), one session-start hook entry in each harness that has a hooks file (Claude Code, Codex; ADR-0010), and the plugins through the harness's own commands. Run the script to refresh them; do not hand patch them, and never hand edit any other setting or hook. Never fetch a `SKILL.md` from GitHub, or run one from a folder the harness did not load, to stand in for a skill (ADR-0011): when a skill does not resolve, say so and show the invocation table in `references/report.md`. Done means source checks pass, the tool's own readbacks agree, and `status --json` has `ok: true` and no manual step (the ChatGPT update: its own report); planned/dispatched work and inaccessible environments are reported separately.
