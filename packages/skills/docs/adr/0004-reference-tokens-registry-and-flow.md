# ADR-0004: Prose references are backticked host-neutral tokens; the registry is generated; flows are authored

Date: 2026-09-30. Status: accepted, amended 2026-10-01 by Justin's decision (oneezy/skills#27, corrections item 8). Decided on oneezy/skills#19 under the autopilot grant.

**Amendment.** The token convention and the authored `flow.yaml` files stand. `skills-registry.json` and the token-resolution check are deferred to a follow-up once the Skills app exists to consume them; until then `check` validates frontmatter, `flow.yaml` against its schema, and generated-file drift. The registry and token sections below describe the deferred design.

## Context

Authored skills name other skills, plugins, apps and files in prose, in several spellings ("call the Skill tool with `oneezy-status`", `/oneezy-merge`). A viewer needs one spelling it can resolve, a registry that says what each name is on each host, and a description of each skill's steps that does not change how any harness runs it. Third-party files are never edited, so their relationships can only be inferred.

## Decision

- **Tokens**: a skill is `/<name>`, a plugin or ChatGPT app is `@<Display Name>`, a file is its path, all in backticks; URLs are bare. A token is an identity; each host's invocation form is looked up, never written into prose.
- **Registry**: `skills-registry.json` is generated by `build --registry` from frontmatter, the manifest, the lock and every `flow.yaml`, committed, and drift-checked by CI. It carries per skill: id, kind, plugin, source, path, model-invocable, host invocation forms, relationships with `need` (required, optional, conditional, example) and `confidence` (confirmed from `flow.yaml`, inferred from prose with file and line), plus `apps`, `duplicates` and `unresolved`.
- **Flow**: `flow.yaml` beside each own `SKILL.md` is authored, validated by `check` against the schema the tool ships, and describes steps with stable ids, sequence, parallel groups and joins, branches, loops and stopping conditions, agent limits, needs, returns and outcomes. Third-party dependency metadata, when authored, lives in `meta/<source>/<skill>.yaml`, outside the snapshot.
- `check` fails on a token that resolves nowhere unless the skill's flow declares it unresolved with a note.

## Consequences

- Own skills gain one file each and a pass over their prose to use the tokens; the wrapper skill's SKILL.md is the first.
- The registry can never disagree with the files because it is not hand-written.
- Nothing in a harness reads `flow.yaml` or the registry; they exist for people and the viewer.
