# References, registry and flow

How an authored document in this library names other things, and how a viewer reads what a skill does. Decided in ADR-0004. Vocabulary: `GLOSSARY.md`.

Status (2026-10-01): the tokens and `flow.yaml` are in force now; the registry and the token-resolution check are deferred until the Skills app exists, so `check` today validates frontmatter, `flow.yaml` and generated-file drift only. The registry section is the design that follow-up will build.

## Reference tokens

| Thing | Token in prose | Example |
|---|---|---|
| a skill, own or third-party | `` `/<name>` `` | `/oneezy-brain`, `/wayfinder` |
| a plugin or a ChatGPT app | `` `@<Display Name>` `` | `@GitHub`, `@Google Drive`, `@Plugin Creator` |
| a file in this repo or beside the skill | `` `<path>` `` | `docs/agents/references.md`, `scripts/sync.sh` |
| a URL | bare | https://github.com/oneezy/skills |

The token is the identity, not an execution command. Read `docs/agents/capabilities.md` for the current host adapter and evidence. Host syntax belongs there; never infer invocation from a display token or assume a mention calls a tool. The registry design below is descriptive metadata, not runtime execution or proof of availability.

Frontmatter, configuration ids, paths and URLs keep their native formats; the token rule is for prose only. A token must resolve in the registry, or the skill's `flow.yaml` declares it under `unresolved` with a note; `check` fails otherwise.

## Registry

`skills-registry.json` at the repo root is generated by `build --registry` and committed; CI fails when it drifts. One entry per working-set skill:

```json
{
  "id": "oneezy-merge",
  "kind": "own",
  "plugin": "oneezy",
  "source": null,
  "path": "skills/oneezy/oneezy-merge",
  "modelInvocable": false,
  "invoke": {
    "claude-code": "/oneezy-merge",
    "claude-code-plugin": "/oneezy:oneezy-merge",
    "codex": "$oneezy-merge",
    "codex-plugin": "$oneezy:oneezy-merge"
  },
  "relationships": [
    { "token": "/oneezy-status", "id": "oneezy-status", "need": "required", "confidence": "confirmed", "when": "step report" },
    { "token": "/pr", "id": "pr", "need": "optional", "confidence": "inferred", "at": "SKILL.md:27" }
  ]
}
```

Third-party entries carry `source`, the upstream path, the lock's commit and hash, and `transforms` (a rename). Top-level sections: `skills`, `apps` (the ChatGPT connector plugins prose may name, with their connector ids from the research notes), `duplicates` (one name from two sources and how the manifest resolves it), `unresolved` (every declared unresolved token with its note and location), `generatedFrom` (manifest and lock hashes).

`need` is one of `required` (the skill cannot finish without it), `optional` (used when present), `conditional` (used when `when` holds), `example` (named only as an example). `confidence` is `confirmed` when the relationship is declared in `flow.yaml` or `meta/`, `inferred` when it was parsed from prose; an inferred relationship records `at` (file and line).

## Flow

`flow.yaml` sits beside an own skill's `SKILL.md`. It describes what the skill does today; it never invents steps and no harness reads it.

```yaml
skill: oneezy-merge
purpose: Land the current branch and end with one status report.
runtime: [git, gh]              # tools and connections the whole skill needs
refs:                           # every reference token the prose uses
  - token: /oneezy-status
    kind: skill                 # skill | plugin | app | file | url
    id: oneezy-status
    need: required              # required | optional | conditional | example
    when: report
unresolved: []                  # tokens with no registry target, each with a note
agents:
  max: 0                        # subagents this skill may create; 0 = none
steps:
  - id: commit-push
    does: stage the session's files, commit, push
    needs: [git]
    outcome: { done: push accepted, fail: push refused → stop }
  - id: open-pr
    after: commit-push
    outcome: { done: PR number returned }
  - id: wait-builds
    after: open-pr
    loop: { until: every Vercel status is success or failure, every: 90s }
    outcome: { done: all green, fail: any failure → skip land and promote }
  - id: land
    after: wait-builds
    if: mode is land or release and all builds green
  - id: promote
    after: land
    if: mode is release
  - id: report
    after: [land, promote]
    calls: { skill: oneezy-status }
    returns: the status report
    outcome: { done: report on screen }
```

Rules the schema enforces: `skill` matches the folder; step ids are unique and `after` names existing ids; a `parallel` step lists member ids and a `join` id; `loop` needs `until`; `if` is free text; `outcome` keys are `done`, `fail`, `input` (the step stops for a human). Everything else is free text kept short. Third-party dependency metadata, when someone authors it, goes in `meta/<source>/<skill>.yaml` with the same `refs` shape, never in `upstream/`.

## Rules added 2026-10-01

From the flow review (`docs/research/flow-review.md`) and Justin's third set of decisions on #27:

- Code fences are exempt from the token rule: `@render`, `@sveltejs/kit` and the like inside a fenced block are code, not references.
- In a multi-word backticked span (`/wayfinder Work through map #<map> …`) the first word is the token; the rest is argument text.
- A path in another repository is written bare (Trident's `packages/ui/AGENTS.md` names a file this library does not hold); a bare path is never a token.
- `need: mention` joins the taxonomy for a skill named as a boundary or as a thing never called (`/wayfinder` in `oneezy-brain`, `/oneezy-merge` in `oneezy-status`). `example` stays for a skill named only as an example.
