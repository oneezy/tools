# Library maintenance

## Agent skills

Own skills live in `skills/<plugin>/<skill>/` in bare Agent Skills form plus a `flow.yaml`; a folder directly under `skills/` with no `SKILL.md` is a group, and its name is the plugin id (`oneezy` for Justin's `oneezy-*` skills, `trident` for the Trident monorepo's). Edit an own skill there and nowhere else: what a machine holds is a harness cache that `npx --yes @oneezy/skills-sync@latest` (source in `oneezy/tools`) replaces from the latest release, and `.agents/skills/` is the uncommitted working set `refresh` writes for `build`. Prose names a skill as `` `/name` ``, a plugin or app as `` `@Name` ``, a file by its path; `flow.yaml` lists the steps, references and outcomes; the rules are in `docs/agents/references.md`.

Third-party skills come from the sources in `skills-sync.json` (`matt-pocock`, `pstack`, `anthropic`, `diagram-design`), snapshotted under `upstream/` and never edited here. `skills-sync.lock.json` records each source's upstream version and commit; a release carries exactly that, so a sync never moves a source. `update` moves one: to the tip of its `ref`, or to the `version` the config holds it at; a `pin` holds one skill at one commit. The library runs it every day over every unheld source, and on demand for one command, in `.github/workflows/run.yml` (ADR-0009, ADR-0014), landing any change through `land/*`. `update` never writes the config: a hold is a config edit landed with the update. The `play` group (`skills/play/`) is the playground; every skill in it is named `play-<name>`. Never remove or deselect a third-party skill to fix a name clash: rename Justin's copy. Authored plugins share the explicit semantic `library.version`; set it deliberately for a release using the emoji-first conventional title rules in `docs/agents/release.md`. Imported plugins retain their locked upstream semantic version, or remain unversioned. The generator never assigns build-count versions or adds a commit hash to a version. Generated and committed, never hand-edited: `skills-sync.lock.json`, `plugins/<id>/`, `dist/hermes/<id>/` (the Hermes rendering of each plugin, which `renderings.hermes` in `skills-sync.json` opts into: the package without `metadata.internal`, which Hermes's loader rejects; `hermes plugins install oneezy/skills/dist/hermes/<id>` installs it), `.claude-plugin/marketplace.json`, `.agents/plugins/marketplace.json`; regenerate them with `npx @oneezy/skills-sync build`, and run `npx @oneezy/skills-sync check` before committing (CI, `.github/workflows/library.yml`, runs the same check on every pull request and only checks; it is a command, never a git hook). Every `main` commit that changes a package is released as `release-<n>` by the same workflow (`docs/agents/release.md`); never tag or publish by hand. A branch named `land/<topic>` lands with no review: `.github/workflows/land.yml` checks it, squashes it into `dev`, promotes `main` and releases; that is how `/oneezy-skills` adds, updates, downgrades and plays with skills, and how `/oneezy-migrate` changes this repo. Changes to `.github/` still go through a pull request. ChatGPT gets the plugins when Justin types one line in ChatGPT, `docs/agents/chatgpt-upload.md`. Generated and ignored: `upstream/`, `artifacts/` and `.agents/skills/`.

## Machines

A machine takes the library from its latest release on GitHub, with no clone of the library on it and no state of its own (ADR-0007, ADR-0012). The tool has two kinds of command:

- **Machine commands** act on the machine they run on: `sync` (the default), `status`, `hook`, `branches`, `unlink`, with `--plan`, `--json`, `--quiet` and `--library owner/repo`. Every caller runs `npx --yes @oneezy/skills-sync@latest <command>` (ADR-0008): the cloud setup script line is `npx --yes @oneezy/skills-sync@latest --quiet`; each harness's session-start hook entry runs `hook` (ADR-0010). An older flag is accepted, does nothing and is named once on stderr. Settings that apply to every machine (which harnesses, which plugins each takes) are the `machines` key of `skills-sync.json`, read at the release's commit; what the machine has is detected on every run.
- **Library commands** change the library: `update`, `add`, `versions`, and `build`, `check`, `refresh`. They run in a checkout, or for the first three from any session through `.github/workflows/run.yml` (ADR-0014; `skills/oneezy/oneezy-skills/references/changes.md`, Dispatch).

`status` is the one answer to "is this machine done": done is `ok: true` and no manual step (`status --json`, `manualSteps`). The manual steps are what only a person can do: switch an account plugin on at claude.ai, trust the Codex hook once, uninstall a Codex plugin that doubles the library's, adopt or delete what sync leaves, replace a cloud environment's old setup line. `/oneezy-skills` ends every run with the open ones, step by step; `/oneezy-status` prints a green or red line per harness.

### Calling a skill

Each harness resolves a skill its own way. When a typed skill does not resolve, show this table (the tool writes the same one into each harness's global instructions file, ADR-0011) instead of improvising:

| Harness | How to call a skill |
|---|---|
| Claude Code | `/<plugin>:<skill>`, e.g. `/oneezy:oneezy-status` |
| Codex | `$<skill>` in the prompt (a plugin's skill: `$<plugin>:<skill>`), the `/skills` picker, or `@<skill>` on ChatGPT web |
| Hermes | `/<skill>` for a loose skill; a plugin's skill: `/agent-plugin-<id>-<hash>:<skill>` |

Never fetch a `SKILL.md` from GitHub, or run one from a folder the harness did not load, to run a skill (ADR-0011): that bypasses the harness's own resolution and `disable-model-invocation`. If a skill is not in the list, run `/oneezy-skills` (or the cloud setup line above), then start a new session.

### Generator output behind an opt-in

The publish guard in `oneezy/tools` (ADR-0008) runs the new tool's `build --check` against this library's `main`, and the library can only rebuild with the tool version that is on npm. So a tool change that alters what `build` writes (a new rendering, new `NOTICE.md` text) ships behind an opt-in key in `skills-sync.json`: without the key the output is byte for byte what it was, the guard stays green and the tool is released first; the library then adds the key and the rebuilt output in one change, built with `@latest`. The first case is `renderings.hermes` (the folder of the Hermes rendering of every plugin, `dist/hermes`; Hermes rejects the `metadata.internal` flag the packages carry); the library carries it from 0.44.0, so `dist/hermes/<id>/` is committed beside every `plugins/<id>/` and released with it. The order matters: an older tool refuses an unknown key (`skills-sync.json is not a valid config: $.renderings: not allowed`), so the key lands only after the tool that knows it is on npm. The second is `adapt` on a source (from 0.13.0): regex find/replace `rules` that `build` applies to that source's Markdown in the package, `forbid` patterns that fail `check` when a term survives, and `allow` lines that may keep one. pstack carries it so Cursor-only wording (the Task tool, AskQuestion, `.cursor/` paths, `pstack-models.mdc`) reads the same in every harness; `upstream/` and the lock keep the original text, and `update` warns when new upstream text adds a forbidden term or a rule stops matching. Treat a new opt-in the same way, and document it here and in the tool's README.
