# Codex hook trust and account-plugin duplicates

## Summary

Codex asks. A user-level hook in `~/.codex/hooks.json` (or inline `[hooks]` in `~/.codex/config.toml`) is a "non-managed" hook: Codex lists it but never runs it until the user reviews and trusts that exact definition, and it asks again whenever the definition changes. Trust is a `sha256:` hash of the normalized handler (event, matcher, command, timeout, statusMessage, async, additionalContextLimit) stored in the user `config.toml` as `[hooks.state."<abs path to hooks.json>:session_start:<group>:<index>"] trusted_hash = "..."`. In the TUI the user meets a full-screen "Hooks need review" picker at startup (Review hooks / Trust all and continue / Continue without trusting), or opens `/hooks`, selects the SessionStart row and presses `t`. Headless `codex exec` skips an untrusted hook silently; only `--dangerously-bypass-hook-trust` runs it. Plugin hooks follow the same flow with a `<plugin>@<marketplace>:hooks/hooks.json:...` key; our plugins ship none.

Yes, a skill shows twice. Codex identifies a plugin as `<name>@<marketplace>`, and ChatGPT account plugins arrive as extra marketplaces (`openai-curated-remote`, `created-by-me-remote`, `workspace-directory`, `workspace-shared-with-me*`) synced into `~/.codex/plugins/cache` when signed in with ChatGPT. The loader de-duplicates only `openai-curated` against `openai-curated-remote`; a plugin installed from the GitHub marketplace `oneezy-skills` and the same plugin on the account both load, and because the skill namespace is the manifest `name`, both produce `oneezy:oneezy-status`. A probe with two local marketplaces listed `probe:probe-hello` twice. Nothing "wins": the model sees both, a typed `$oneezy:oneezy-status` resolves to the first in list order, and the `$`/`/skills` popup shows both. The GitHub flow itself works on 0.162.1: `codex plugin marketplace add oneezy/skills` snapshots `main`, `codex plugin add oneezy@oneezy-skills` installs 0.43.1 into the cache, `marketplace upgrade` re-clones when the remote revision moved and force-reinstalls every installed plugin from that marketplace; Codex also runs that upgrade in the background at startup. `~/.codex/skills` (deprecated) and `~/.agents/skills` are both still read.

## Facts

### 1. Where user hooks live and what they look like

- Codex loads `hooks.json` from the config folder of every active config layer plus inline `[hooks]` tables; for the user layer that is `$CODEX_HOME/hooks.json` next to `$CODEX_HOME/config.toml` (`~/.codex/` by default), for a project `<repo>/.codex/hooks.json`. [hooks.md "Where Codex looks for hooks"; `hooks/engine/discovery.rs:146-152` (`layer.hooks_config_folder()` then `load_hooks_json`), `:343` (`config_folder?.join("hooks.json")`); `config/state.rs:219-243` (user layer `config_folder` = parent of its `config.toml`)] verified
- Both representations in one layer are merged with a startup warning; several layers all run ("Higher-precedence config layers don't replace lower-precedence hooks"). Project-local hooks load only in trusted projects. [hooks.md; `discovery.rs:154-163`] verified
- Schema: `{"description"?: "...", "hooks": {"<Event>": [{"matcher"?: "<regex>", "hooks": [{"type": "command", "command": "...", "timeout"?: <seconds>, "statusMessage"?: "...", "async"?: bool, "additionalContextLimit"?: <tokens>, "commandWindows"?: "..."}]}]}}`. The event key is spelled `SessionStart` (`#[serde(rename = "SessionStart")]`, `config/hook_config.rs:47`); events: `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `UserPromptSubmit`, `SubagentStart`, `SubagentStop`, `Stop`, `Interrupt`, `SessionStart`, `SessionEnd`. `SessionStart`'s `matcher` filters `source`: `startup`, `resume`, `clear`, `compact`. `timeout` defaults to 600 s; commands run with the session `cwd`; plain stdout "is added as extra developer context", JSON stdout may carry `hookSpecificOutput.additionalContext`. [hooks.md "Config shape", "SessionStart"] verified
- Hooks are on by default (`[features] hooks`, deprecated alias `codex_hooks`). [hooks.md "Turn hooks off"; config-reference.md:491-494] verified
- `codex --help` (0.162.1) carries `--dangerously-bypass-hook-trust`: "Run enabled hooks without requiring persisted hook trust for this invocation. DANGEROUS. Intended only for automation that already vets hook sources". `codex hooks --help` is not a subcommand (prints the top-level help). [help output] verified

### 2. The trust mechanism

- Docs: "Non-managed hooks must be reviewed and trusted before they run." "Codex records trust against the hook's current hash, so new or changed hooks are marked for review and skipped until trusted." Managed hooks (system, MDM, cloud, `requirements.toml`) are trusted by policy. [hooks.md "Review and trust hooks"] verified
- Key: every handler gets `<key_source>:<event_key>:<group_index>:<handler_index>`, where `key_source` for a file hook is the absolute path of the `hooks.json` or `config.toml` as displayed, and `event_key` for SessionStart is `session_start`. Example: `/home/justin/.codex/hooks.json:session_start:0:0`; a plugin hook's key source is `<plugin>@<marketplace>:hooks/hooks.json`. [`hooks/lib.rs:95-123`; `discovery.rs:174, 667`; `declarations.rs:35-37` and its test (`demo@test:hooks/hooks.json:session_start:0:0`)] verified; Windows spelling `C:\Users\Justin\.codex\hooks.json:session_start:0:0` inferred from `Path::display()`
- Hash: `sha256:<hex>` over the normalized identity `{event_name, matcher, hooks: [normalized handler]}` serialized to JSON with sorted keys, "so equivalent hooks from config TOML and hooks.json converge on the same trust identity". The normalized command handler keeps `command` (on Windows `commandWindows` replaces it), `timeout` (default filled in), `async`, `statusMessage`, `additionalContextLimit` (dropped when it equals the default 2500). Changing any of those, or the matcher, changes the hash; changing the file's `description` or key order does not; moving the entry to another group or index changes the key, which counts as a new hook. [`discovery.rs:666-667, 769-794`; `config/fingerprint.rs:54-66`] verified (consequences inferred from the code)
- State: `[hooks.state."<key>"]` with `trusted_hash = "sha256:..."` and optional `enabled = false`, read only from the user `config.toml` and session flags ("Project, managed, and plugin layers can discover hooks, but they do not get to write user hook state"). Status: builtin -> Trusted; managed -> Managed; stored hash equals current -> Trusted; stored but different -> Modified; none -> Untrusted. Enabled unless `enabled = false`. A handler is added to the runnable set only when enabled and (bypass flag or Managed/Trusted). [`hooks/config_rules.rs:9-63`; `config/hooks_tests.rs:195-199` (TOML example); `discovery.rs:680-682, 715-722, 796-821`] verified
- The TUI persists trust through the app-server `config/batchWrite` with `key_path: "hooks.state"`, value `{"<key>": {"trusted_hash": "<current_hash>"}}`, `file_path: None`, which lands in the user `config.toml` ("config.toml should be updated even when file_path is omitted"). `hooks.state` is not in the public configuration reference. [`tui/hooks_rpc.rs:58-92`; `app-server/config_manager_service_tests.rs:1215-1236`; config-reference.md grep] verified
- Plugin hooks: "Installing or enabling a plugin doesn't automatically trust its hooks. Plugin-bundled hooks are non-managed hooks, so Codex skips them until the user reviews and trusts the current hook definition." Same review flow, source label `Plugin - <name>@<marketplace>`, env `PLUGIN_ROOT`, `PLUGIN_DATA` (+ `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA`). The app-server also has a code path that writes `trusted_hash` for plugin hooks during an "effective plugin change" ("materialization-owned hook trust" of remote plugin bundles); its reach is an open question and irrelevant here because the library's plugins ship no `hooks/`. [build-plugins.md:907-909; hooks.md "Plugin-bundled hooks"; `discovery.rs:244-296`; `app-server/effective_plugin_change.rs:88-147`; `remote_installed_plugin_sync.rs:62-63`] verified
- Cloud-orchestrated ChatGPT Work threads do not run command hooks at all ("Command/shell, prompt, and agent handlers; hooks from local configuration, plugins, or local directories ... are not supported with cloud orchestration"); this matches ADR-0010's "cloud sessions never read user hooks". [hooks.md "Managed hooks from requirements.toml"] verified

### 3. What the user sees and does (TUI, source at cc7ba336)

- At `codex` startup, when any hook is Untrusted or Modified and `--dangerously-bypass-hook-trust` is not set, a full-screen picker replaces the composer:

  ```
  Hooks need review
  1 hook is new or changed.
  Hooks can run outside the sandbox after you trust them.

  › 1. Review hooks
    2. Trust all and continue
    3. Continue without trusting (hooks won't run)

    enter confirm · esc skip
  ```

  "Trust all and continue" requires an explicit confirmation and writes `trusted_hash` for every hook needing review; "Continue without trusting" starts the session with those hooks skipped; "Review hooks" opens the hooks browser. The same check runs after a directory change and after resume-time config reloads. [`tui/lib.rs:2072-2080`; `startup_hooks_review.rs:231-277` and snapshot `startup_hooks_review_prompt`; `app/working_directory.rs:633-638`; `app/resume_config.rs:237-280`] verified

### 4. Duplicates: GitHub marketplace plugin and the same plugin on the ChatGPT account

- Plugin identity is `<name>@<marketplace>` (`[plugins."oneezy@oneezy-skills"] enabled = true`). Account plugins are modelled as remote marketplaces: `openai-curated-remote` ("OpenAI Curated Remote", directory installs on the account), `created-by-me-remote` ("Created by me", personal plugins), `workspace-directory` ("Workspace Directory", a business workspace's plugins including imported GitHub marketplaces), `workspace-shared-with-me`, `-private`, `-unlisted`. When Codex is signed in with ChatGPT it syncs the account's installed plugin bundles in the background into `$CODEX_HOME/plugins/cache/<remote marketplace>/<plugin>/<version>` and merges them into the configured plugin set at startup; with an API key or no login the sync returns `AuthRequired` / `UnsupportedAuthMode`. [`core-plugins/remote.rs:93-104, 2347-2355`; `remote/remote_installed_plugin_sync.rs:116-139`; `manager.rs:2904-2915`; `loader.rs:247-303`] verified (source; the signed-in half was not exercised)
- The only cross-marketplace de-duplication is curated vs remote-curated: with the remote global catalog active, configured `*@openai-curated` entries are dropped in favour of `*@openai-curated-remote`, and `sites@openai-bundled` yields to `sites@openai-curated-remote`; otherwise a remote curated plugin is skipped when a local curated copy of the same name is installed. A user-configured marketplace such as `oneezy-skills` is never compared with a remote one, so `oneezy@oneezy-skills` and `oneezy@created-by-me-remote` (or `@workspace-directory`) both load and both are enabled. [`loader.rs:247-303`] verified
- Skill namespace is the manifest `name`, not the marketplace: plugin skill roots carry `plugin_namespace = manifest.name` (remote: `plugin_id.plugin_name`), so both copies yield `oneezy:oneezy-status`. Probe: two local marketplaces `mkt-a` and `mkt-b`, each with a plugin named `probe`, both installed; `codex debug prompt-input` listed `probe:probe-hello: Says hello from mkt-a. (file: r1/probe/0.1.0/skills/probe-hello/SKILL.md)` and `probe:probe-hello: Says hello from mkt-b. (file: r2/...)`, two lines, same name. Docs: "If two skills share the same `name`, Codex doesn't merge them; both can appear in skill selectors." [`loader.rs:920, 1076, 1404`; `remote.rs:1692`; `utils/plugins/lib.rs:35-41`; probe; build-skills.md:135] verified
- Which one "wins": none. The model receives both lines (catalog order: scope rank, then name, then path; plugin roots appeared in marketplace-name order in the probe). A typed `$oneezy:oneezy-status` resolves to the first enabled skill with that name in the skills list (`seen_names`); picking from the `$`/`/skills` popup links the chosen entry's path, which resolves ahead of plain names. Only cloud-orchestrated ChatGPT Work threads prefer the cloud copy over a same-named local `plugin:skill` entry; that path is not Codex CLI's. [`ext/skills/render.rs:48-63`; `tui/chatwidget/skills.rs:204-256`; `ext/skills/render_dedup.rs:39-53`; `world_state_catalogs.rs:273`] verified (resolution); inferred (which copy is first)
- Invocation: in Codex, `/skills` or `$` mentions (`$skill-creator`); plugin skills are namespaced `<plugin>:<skill>` and plugins themselves are `$` mentions when installed, enabled and not admin-disabled; in ChatGPT web, desktop and mobile, `@` mentions ("Type `@` to invoke the plugin or one of its bundled skills explicitly"); "ChatGPT supports `@` mentions, while Codex supports `$` mentions for skills." [build-skills.md:92-113; plugins.md "Choose a specific plugin"; skills-and-plugins.md; `tui/app/plugin_mentions.rs:38-53`] verified
- `codex plugin list` covers "plugins available from configured and remote marketplaces", so a signed-in `codex plugin list --json` is the one place that shows an account copy next to the GitHub copy; `codex plugin remove <name>@<remote marketplace>` uninstalls a remote plugin through the service (needs auth). [`codex plugin list --help`; `cli/plugin_cmd.rs:655-690`] verified (CLI paths); inferred (that this is the right cleanup for Justin's account)

## What tools#150 and tools#151 must do

**tools#151 (one session hook per harness).** There is a trust step for Codex; the tool cannot complete it.

1. Write the entry into `$CODEX_HOME/hooks.json` (default `~/.codex/hooks.json`, Windows `%USERPROFILE%\.codex\hooks.json`), creating the file as `{"hooks": {}}` when absent, and append one matcher group to `hooks.SessionStart`:

   ```json
   {"matcher": "startup|resume", "hooks": [{"type": "command", "command": "npx --yes @oneezy/skills-sync@latest hook", "statusMessage": "Skills Sync", "timeout": 120}]}
   ```

   Append, never insert or reorder: existing groups keep their `group_index`, so their trust stays valid. Keep every field byte-stable afterwards (command, matcher, statusMessage, timeout), because any change makes Codex ask again. Recognize the own entry by its `command`. Do not add `clear|compact` to the matcher (that would run the sync on every compaction). The `hook` command must write nothing to stdout when nothing changed, since stdout becomes developer context for the model; report to stderr.
2. Do not write `hooks.state` yourself: the hash is Codex's internal normalization and pre-trusting defeats the review. Do not use `--dangerously-bypass-hook-trust`.
3. Detect the trust state by reading `$CODEX_HOME/config.toml`: a table `[hooks.state."<abs path of hooks.json>:session_start:<group>:0"]` with a `trusted_hash` whose group index is the own entry's position means Justin has trusted it (Codex re-marks it Modified only if the entry changes, which the tool never does). Absent: report "Codex hook needs trust" as an open manual step. Per machine and per WSL distro, since each has its own `CODEX_HOME`.
4. Manual steps for the `/oneezy-skills` list (Codex 0.162.1 TUI), once per machine or distro:
   1. In a terminal run `codex` in any folder.
   2. If the screen `Hooks need review` appears, choose `1. Review hooks` and press Enter. (If the only new or changed hook is the Skills Sync one, `2. Trust all and continue` plus its confirmation is the same thing.)
   3. In the `Hooks` table select `SessionStart` and press Enter.
