# Claude Code plugins and marketplaces

## Summary

A plugin is a directory with an optional `.claude-plugin/plugin.json` (only `name` required) and components in fixed folders (`skills/<name>/SKILL.md`, `agents/`, `hooks/hooks.json`, `.mcp.json`); a marketplace is a repo or folder whose `.claude-plugin/marketplace.json` lists plugins and a `source` for each. `github` sources take `repo`, `ref` (branch or tag), `sha`, and no `path`; a subdirectory of another repo needs `git-subdir` (`url`, `path`, `ref`, `sha`). `/plugin marketplace add owner/repo[#ref]` clones the repo (default branch unless `#ref`) with the machine's own git credentials, so a private GitHub repo works after `gh auth login` + `gh auth setup-git`; `/plugin marketplace update <name>` re-fetches the catalog, and a plugin copy changes only when its computed version changes. Plugin skills are always `/<plugin>:<skill>`; every SKILL.md frontmatter field, including `disable-model-invocation` and `argument-hint`, applies in a plugin; a same-named user skill does not collide because of the namespace. `claude plugin validate <path>` (`--strict`, `--json`, exit 0/1/2) checks a plugin or marketplace; local testing is `--plugin-dir <dir>` (session-only) or `claude plugin marketplace add ./dir` + `claude plugin install x@name`; scopes are user/project/local with local > project > user.

## Facts

### 1. Plugin layout and `plugin.json`

- Manifest lives at `.claude-plugin/plugin.json` under the plugin root; every other file (`skills/`, `commands/`, `hooks/`) goes at the plugin root, not inside `.claude-plugin/`. The manifest is optional: without it the components in the standard layout load and the name comes from the marketplace entry or, with `--plugin-dir`, the directory name. Source: manifest-reference#manifest-file. verified.
- `name` is the only required key. It must be non-empty with no spaces, `@`, `:`, path separators, control or bidi characters; kebab-case is recommended and a non-kebab name is a validate warning. Every component is namespaced under it. Source: manifest-reference#name. verified.
- Other top-level fields: `$schema`, `displayName`, `version` (string, not semver-checked; setting it pins users until it changes), `description`, `author` (object; `name` required, `email`/`url` optional), `homepage` (must parse as a URL or the plugin fails to load), `repository` (not validated), `license` (SPDX), `keywords` (array), `metadata` (free-form, ignored), `defaultEnabled` (default true), `dependencies`, `settings`, `userConfig`, `channels`, `skills`, `commands`, `agents`, `hooks`, `mcpServers`, `lspServers`, `outputStyles`, `workflows`, `experimental.{themes,monitors,evals}`. Source: manifest-reference#fields. verified.
- Component path keys: `skills` is a path or array of directories (each a dir of `<name>/SKILL.md` folders, or one folder holding SKILL.md; `"."` = plugin root) and ADDS to the default `skills/` scan; `commands`, `agents`, `outputStyles`, `workflows` REPLACE their default folder; `hooks`, `mcpServers`, `lspServers` MERGE with `hooks/hooks.json`, `.mcp.json`, `.lsp.json`. `agents` entries must be `.md` files, directories not accepted. Source: manifest-reference#how-each-key-combines-with-its-default-location, #path-only-fields. verified.
- Every manifest path is relative to the plugin root, must start with `./`, must exist, and must resolve inside the root (`..` fails validation as path traversal). Source: manifest-reference#path-rules. verified.
- Standard layout: `skills/` (one `<name>/SKILL.md` per skill), `commands/` (older form, "prefer skills/"), `agents/`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `output-styles/`, `workflows/`, `themes/`, `monitors/monitors.json`, `bin/` (on Bash PATH while enabled), `settings.json`. A `CLAUDE.md` at the plugin root is not loaded and triggers a validate warning. Source: manifest-reference#standard-layout. verified.
- A plugin with `SKILL.md` at its root, no `skills/`, and no `skills` key loads as a single skill; set frontmatter `name` there or a marketplace install names it after its cache directory. Source: components#skills; manifest-reference#standard-layout. verified.
- Unrecognized top-level manifest keys are stripped with a validate warning; unknown keys inside `userConfig`, `channels`, `lspServers`, `monitors` entries are errors. Source: manifest-reference#unrecognized-fields. verified.
- Local check: a manifest with only `{ "name": "oneezy-probe" }` gives `Validation passed with warnings` (missing version, description, author); the same run with `--strict` prints `Validation failed (--strict treats warnings as errors)` and exits 1. Source: probe run on this machine, Claude Code 2.1.286. verified.

### 2. `marketplace.json` and plugin sources

- File location: `.claude-plugin/marketplace.json`; the directory containing `.claude-plugin/` is the marketplace root and every relative source resolves from it. Keeping the file elsewhere forces users to declare the marketplace in `extraKnownMarketplaces` with a `path`, because `marketplace add` has no option for it. Source: marketplace-reference#marketplace-file. verified.
- Required top-level keys: `name`, `owner` (object, `name` required), `plugins` (array). Optional: `$schema`, `description` (warning if missing), `version`, `metadata.description`, `metadata.version`, `metadata.pluginRoot` (bare source names resolve under it, v2.1.239+), `forceRemoveDeletedPlugins`, `allowCrossMarketplaceDependenciesOn`, `renames`. Source: marketplace-reference#top-level-fields. verified.
- Marketplace `name` rules: letters, digits, `.`, `_`, `-`; starts with a letter or digit; no `..`. It is the half after `@` in every plugin id. Reserved: the official/community names, `inline`, `builtin`, `skills-dir`, `synced`, `claude-plugin-test`, `npm`, `pip`, `uv`, `cargo`, `github`, `gh`, anything starting `claudeai-`, and look-alikes of official names. Source: marketplace-reference#reserved-names. verified.
- Plugin entry: `name` and `source` required; entry `name` allows letters, digits, `.`, `_`, `-`, starting with a letter or digit. Optional: `description`, `version`, `category`, `tags`, `strict` (default true), `relevance`, `dependencies`, `defaultEnabled`, `displayName`, `metadata`, `headers`, `headersHelper`, plus any `plugin.json` field. Source: marketplace-reference#plugin-entries. verified.
- Keep entry `name` equal to the manifest `name`: the entry name is the install id (`<entry>@<marketplace>`, the `enabledPlugins` key, the cache dir name); the manifest name is the skill prefix. If they differ, installing by the manifest name fails with `Plugin "<manifest-name>" not found in marketplace`. Source: create-marketplace#keep-the-entry-name-and-the-manifest-name-the-same; loading#entry-name-and-manifest-name. verified.
- Source forms: relative path string (`"./plugins/x"`, must start `./`, `"."` = root, `..` fails); `{source:"github", repo:"owner/repo", ref?, sha?}`; `{source:"url", url:<full git URL https/http/file/git@>, ref?, sha?}` (no owner/repo shorthand); `{source:"git-subdir", url:<git URL or owner/repo>, path:<subdir>, ref?, sha?}` fetched with a sparse partial clone; `{source:"npm", package, version?, registry?}` (install scripts never run); `{source:"archive", url:<https zip>, sha256?}` (v2.1.224+); `{source:"command", command, timeout?, mode?}` (v2.1.229+). Source: marketplace-reference#plugin-sources. verified.
- A `github` plugin source has fields `repo`, `ref`, `sha` "and no `path`". `ref` is a branch or tag and defaults to the repository's default branch; `sha` is a full 40-char lowercase commit and wins when both are set. So: branch or tag yes; subdirectory no (use `git-subdir`). Source: marketplace-reference#marketplace-sources table and #plugin-sources. verified.
- Relative-path sources only resolve when Claude Code has the marketplace files (`github`, `git`, `file`, `directory` marketplace sources). A marketplace added as a bare `marketplace.json` URL downloads only that file, so its entries need object sources. Source: marketplace-reference#relative-path-plugin-source; host-marketplace#avoid-relative-path-entries-in-a-url-hosted-marketplace. verified.
- Entry vs `plugin.json`: with no `plugin.json` the entry is the manifest; with one present and `strict: true` (default) the entry's `commands`/`agents`/`skills`/`outputStyles`/`themes` are appended and its `hooks` replace per event; `strict: false` plus any component field is a load-failing conflict. Entry `mcpServers`, `lspServers`, `userConfig`, `channels` never apply when `plugin.json` exists. `version` in `plugin.json` beats the entry; entry `displayName`/`defaultEnabled` beat the manifest. Source: marketplace-reference#strict-mode; manifest-reference#metadata-precedence. verified.

### 3. Adding, fetching, updating, private repos

- `/plugin marketplace add <source>` and `claude plugin marketplace add <source>` accept: `owner/repo`, `owner/repo#ref`, `owner/repo@ref` (type `github`, "clones the GitHub repository, pinned to ref when given"); `user@host:path[.git][#ref]` and `https://.../x.git[#ref]` (type `git`); other https URLs (type `url`, fetches marketplace.json only); `./path`, `../path`, `/path`, `~/path` to a directory or `.json` file (`directory`/`file`, read in place). Flags: `--scope user|project|local` (default user), `--sparse <paths...>`, `--claudeai`. Source: cli-reference#plugin-marketplace-add; local `claude plugin marketplace add --help`. verified.
- Default ref: the marketplace-source `ref` "defaults to the repository's default branch"; `#ref` pins a branch or tag. Source: marketplace-reference#fields-by-type; install#add-a-marketplace. verified.
- It is a clone of the repo: the clone lands in `~/.claude/plugins/marketplaces/<name>/`; host-marketplace says a git-hosted marketplace makes Claude Code "clone the whole tree"; `--sparse .claude-plugin plugins` limits the checkout for monorepos; the clone has a 120 s default timeout (`CLAUDE_CODE_PLUGIN_GIT_TIMEOUT_MS`). LFS content is never fetched. Whether the clone is shallow is not documented. Source: loading#find-plugins-on-disk; host-marketplace; troubleshooting#git-clone-timed-out-after-120s. verified (shallow-ness: unknown).
- The registered name comes from the `name` field in marketplace.json, not the repo name. Install id is `<entry>@<marketplace-name>`. Source: host-marketplace#host-your-marketplace. verified.
- Updates: `claude plugin marketplace update [name]` / `/plugin marketplace update <name>` refreshes the catalog; a marketplace added with a `ref` updates to the latest commit of that ref, not the default branch. `claude plugin update <plugin>@<marketplace>` updates one plugin. Background auto-update is OFF by default for every non-Anthropic marketplace; a user turns it on per marketplace in `/plugin` > Marketplaces. Installing `name@marketplace` refreshes that marketplace first unless it was added from a local file/directory. Source: cli-reference#plugin-marketplace-update; install#keep-plugins-updated; loading#when-claude-code-refreshes-a-marketplace-before-an-install. verified.
- A user gets a new plugin copy only when the computed version changes: `plugin.json` `version` first, then entry `version`, else for `github`/`url`/`git-subdir` the 12-char commit SHA (a `git-subdir` version also carries a hash of the subdirectory path), for a relative path inside a git-hosted marketplace the commit SHA of the installed directory, for a local non-git directory `unknown`. Omit `version` in both places to track commits. Source: loading#how-claude-code-computes-the-version; host-marketplace#release-a-new-version. verified.
- Plugins from a marketplace added as a local directory load IN PLACE (no copy, edits apply at next start or `/reload-plugins`, no version bump); every other marketplace plugin is copied to `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`. Source: loading#in-place-and-copied-plugins. verified.
- Private repo: Claude Code runs the machine's own `git` with prompts suppressed; it has no token of its own and marketplace.json has no auth field. For `owner/repo` it probes `ssh -T git@github.com`, clones over SSH if that works, else HTTPS; `CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1` skips the probe. HTTPS needs a stored credential (`gh auth login` then `gh auth setup-git`); SSH needs a passphrase-free key and a `known_hosts` entry. The same credentials serve install, update, and background auto-update; a `GITHUB_TOKEN` env var alone does not authenticate, only via a credential helper. Source: host-marketplace#grant-access-to-a-private-marketplace; install#add-a-private-marketplace. verified.
- Registering for a repo's collaborators: `claude plugin marketplace add owner/repo --scope project` writes `.claude/settings.json`; each collaborator still installs locally. Cloud sessions (claude.ai/code) load neither local plugins nor `extraKnownMarketplaces`. Source: host-marketplace#register-the-marketplace-for-everyone-in-a-repository; loading#plugins-shared-through-a-repository. verified.
- This machine currently has one registered marketplace, `claude-plugins-official` (github anthropics/claude-plugins-official), no `cache/` dir, and four `@synced` plugins from claude.ai. Source: ~/.claude/plugins/known_marketplaces.json; `claude plugin list`. verified.

### 4. Skill invocation and namespacing inside a plugin

- Command name is `/<plugin>:<directory>`; frontmatter `name` replaces the last segment and the prefix stays (`skills/review/SKILL.md` with `name: fancy` in `my-plugin` -> `/my-plugin:fancy`). A `name` already carrying `my-plugin:` is not doubled on v2.1.246+. `commands/db/migrate.md` -> `/my-plugin:db:migrate`. Source: skills#how-a-skill-gets-its-command-name; components#skills, #commands. verified.
- Docs on the bare form: "The bare `/fancy` also invokes the skill unless another command already uses that name" (stated ONLY for a plugin skill with frontmatter `name`; the command-name table promises no bare form for a directory-named plugin skill, only `/my-plugin:review`). The same page says a plugin skill "keeps its bare command" in non-interactive sessions when named `help` or `feedback`, so the docs treat bare invocation as present under `-p` too. Source: skills#how-a-skill-gets-its-command-name (table plus the two paragraphs after it). verified (as a docs claim).
- Local test contradicts the frontmatter-name half in `-p` mode: with `claude --plugin-dir <probe> -p`, `/oneezy-probe:hello` and `/oneezy-probe:probenamed` ran the skills (replies `PROBE-OK`, `NAMED-OK`); bare `/probenamed` (frontmatter name) was not expanded (Claude reported the skill "was not actually invoked by the harness"). Bare `/hello` (directory name) got "`/hello` isn't installed in this session, so nothing ran", but that is consistent with the docs, which never promise a bare directory name for a plugin skill. Interactive mode was not tested. Source: probe runs on Claude Code 2.1.286 (MSYS_NO_PATHCONV=1 to stop Git Bash rewriting `/hello`). verified for -p; interactive: unknown.
- Collisions: "A plugin skill and a skill at any of [enterprise/personal/project] locations: both load, because plugin skills are namespaced as `/plugin-name:skill-name`." Between plugins that share a MANIFEST name the order is managed-settings > `--plugin-dir`/`--plugin-url`/`CLAUDE_CODE_PLUGIN_DIRS` > installed marketplace plugin > skills-dir plugin (`~/.claude/skills/` beats project `.claude/skills/`) > `@synced`. Source: skills#resolve-skills-that-share-a-name; loading#name-conflicts. verified.
- Frontmatter: "Claude Code skills at any level, including plugin skills: every field in the table", so `disable-model-invocation`, `argument-hint`, `arguments`, `user-invocable`, `allowed-tools`, `model`, `context: fork`, `hooks`, `paths` all apply in a plugin. `disable-model-invocation: true` keeps the description out of context and blocks Claude from calling it; `user-invocable: false` hides it from `/`. Source: skills#using-skill-frontmatter-outside-claude-code; #control-who-invokes-a-skill. verified.
- Context cost: for each skill/agent/command Claude may invoke, name + description sit in context every turn while the plugin is enabled; `claude plugin details <name>` prints the always-on token count. Source: plugins/overview#what-an-enabled-plugin-adds-to-your-sessions. verified.
- A plugin can also be a folder under `~/.claude/skills/<name>/` (or project `.claude/skills/<name>/`) that contains `.claude-plugin/plugin.json`: it loads every session as `<name>@skills-dir` with no marketplace. Its root SKILL.md is also a personal skill, invoked as `/my-tool` (not `/my-tool:my-tool`); skills under its `skills/` get the prefix. `claude plugin init <name>` scaffolds one. Source: create#make-a-plugin-load-in-every-session; loading#find-where-a-plugin-came-from. verified.

### 5. Validation, local install, scopes, enable/disable

- `claude plugin validate <path> [--strict] [--json]`; `/plugin validate <path>` prints the same inline. Given a directory it checks `.claude-plugin/marketplace.json` if present, else `.claude-plugin/plugin.json`, else component files by folder name (`skills`, `agents`, `commands`, or a `.claude` dir). Exit 0 passed (or with warnings), 1 failed (or warning under `--strict`), 2 validator error. It does not follow symlinks (linked skill entries are skipped with a warning; a linked `skills` dir itself is an error), and a marketplace run does not open the listed plugins' skill files. Source: cli-reference#plugin-validate; local `--help`. verified.
- `claude plugin validate ./skills` in this worktree: `Validating components in: ...\skills` -> `Validation passed`. Source: local run. verified.
- Local install loop: `claude plugin marketplace add ./my-marketplace` (prints `declared in user settings`), `claude plugin install my-first-plugin@my-marketplace` (default scope user), `claude plugin list`, `claude plugin details <manifest-name>`; `claude plugin marketplace remove <name>` uninstalls its plugins too. In a session, `/plugin install x@m` opens the details pane to pick a scope rather than installing outright. Source: create-marketplace#create-a-marketplace. verified.
- Session-only load: `claude --plugin-dir <plugin-root-or-.zip>` (repeatable; a folder of plugins loads each child with a manifest, v2.1.265+; pointing it at a marketplace root loads nothing), `--plugin-url <zip>`, or `CLAUDE_CODE_PLUGIN_DIRS` (v2.1.280+). Appears as `<name>@inline`, `Version: unknown`, `Status: loaded` in `claude --plugin-dir <p> plugin list`; nothing is written to settings; `/reload-plugins` applies edits; the `userConfig` dialog does not appear this way. Source: create#develop-without-a-marketplace; cli-reference#flags-that-load-a-plugin-for-one-session; local probe. verified.
- Scopes: user writes `enabledPlugins` in `~/.claude/settings.json`; project writes committed `.claude/settings.json` (collaborators still run `claude plugin install x@m --scope project` once); local writes `.claude/settings.local.json`. Precedence local > project > user. `claude plugin install|uninstall` default to user; `enable|disable` act on the most specific scope that lists the plugin; all take `--scope`. `/plugin enable|disable|uninstall <plugin>` open the Installed tab and act there; closing the panel runs `/reload-plugins`. Source: install#choose-an-install-scope, #manage-plugins-from-your-shell; cli-reference#plugin-in-a-session. verified.
- `defaultEnabled: false` installs the plugin off until `claude plugin enable`. `/plugin` is unavailable under `claude -p`; shell `claude plugin ...` commands still work there. Source: install#choose-an-install-scope, #other-places-you-run-claude-code. verified.
