# Claude desktop app and account plugins

## Summary

The claude.ai account plugins reach every Claude Code surface Justin uses, but by two different routes. The terminal CLI (and the JetBrains plugin, which runs that same `claude`) syncs them itself in the background on every start from Claude Code 2.1.273 on, into `~/.claude/plugins/synced/`, as `<name>@synced`, lowest in the name-conflict order, so a CLI-installed plugin with the same manifest name hides the account copy there. Cloud sessions and Cowork download them when the session starts; this container (2.1.296) lists nine `@synced` plugins, loaded, with no install record of any other plugin. The desktop app's Code tab is documented as receiving them too, but the desktop app "manages" those plugins "itself" and hands them to its local Code sessions through the route `disableSideloadFlags` blocks, not through the CLI's sync; the docs never show the id they carry in that session, nor where they rank against a CLI-installed copy, and the Code tab runs its own bundled Claude Code whose version differs from the terminal's. Those two points, and whether a user-level `CLAUDE_CONFIG_DIR` reaches the Code tab, are the only things left to a run on the PC. WSL sessions in the Code tab get no plugins at all. Chat and Cowork read plugins only from the account, so nothing on the PC can hide them there. `syncClaudeAiPlugins: false` (user, local or managed settings) turns the CLI sync off and trashes what it synced; token credentials (`ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `apiKeyHelper`, an API key), `--bare`, `--safe-mode`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` and `--setting-sources` without `user` skip it. For tools#149 no second form is needed: moving Claude Code to account plugins only removes the one thing that hides them; the fallback is the marketplace plugin form the tool has today, kept per machine when the PC check fails, never loose links, because `~/.claude` is shared between the terminal and the Code tab and loose links would list every skill twice again.

## Facts

### 1. Terminal CLI

- "A plugin you turn on for your claude.ai account also loads in Claude Code, alongside the plugins you install from marketplaces. [...] Each of these plugins loads as `<name>@synced`, with no marketplace and no install record." Terminal sessions: "each time you start Claude Code, it syncs once in the background, downloading new and updated plugins and removing the ones that you or your organization turned off. Syncing in terminal sessions requires Claude Code v2.1.273 or later". Source: loading#synced-plugins. verified.
- Changelog: 2.1.273 "Changed sign-in with a Claude account to also request access to your claude.ai plugins"; 2.1.275 "Added syncing of the skills and plugins enabled on your claude.ai account to terminal sessions signed in with it; opt out with `syncClaudeAiSkills: false` or `syncClaudeAiPlugins: false`". The docs' floor is 2.1.273, the shipping entry is 2.1.275; a sign-in made on an earlier version "doesn't cover plugins until Claude Code renews it in the background. To get access sooner, run `/login` again." Source: CHANGELOG; loading#sign-in-requirements-for-terminal-sync. verified.
- The sync "can finish after your session has started"; the session then shows `Plugins changed. Run /reload-plugins to activate.` A plugin enabled on claude.ai while a session runs downloads at the next start. Source: loading#sync-timing-in-terminal-sessions. verified.
- Name conflicts compare manifest names, highest first: managed `enabledPlugins`; `--plugin-dir`/`--plugin-url`/`CLAUDE_CODE_PLUGIN_DIRS`; installed marketplace plugin; skills-directory plugin; "5. A plugin synced from claude.ai. When an enabled plugin from any other origin matches its name, Claude Code loads that plugin and reports the synced copy as not loaded. To use the claude.ai copy instead, disable your own copy". So the tool's `oneezy@oneezy-skills` (manifest name `oneezy`) hides `oneezy@synced` in the terminal; disabling it is enough, uninstalling is cleaner. Source: loading#name-conflicts. verified.
- Opt-out for a machine: `syncClaudeAiPlugins: false` in user settings, `.claude/settings.local.json`, managed settings or `--settings`; "Claude Code honors only `false`: `true` is the same as unset"; a `false` in a repository's `.claude/settings.json` is ignored ("A repository can't turn it off for you"). With `false`, Claude Code "stops downloading synced plugins and stops loading the ones already in `~/.claude/plugins/synced/`. In user or managed settings, it also moves them to `~/.claude/plugins/.trash/`". Requires 2.1.273. Per plugin: `claude plugin disable <name>@synced` writes `"<name>@synced": false` into user `enabledPlugins`. Source: settings-reference#syncclaudeaiplugins; settings.md precedence table row; loading#control-which-synced-plugins-load. verified.
- Sessions that neither download nor load synced plugins, "even after you sign in with `/login`": a credential from `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` or an `apiKeyHelper` script; no feature-flag fetch (`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, Bedrock); `--bare` or `--safe-mode`; a `--setting-sources` list without `user`. The skills page adds "one that authenticates with an API key" to the same list. `--bare` (2.1.81) "skips hooks, LSP, plugin sync, and skill directory walks; requires `ANTHROPIC_API_KEY` or an `apiKeyHelper`". Source: loading#sign-in-requirements-for-terminal-sync; skills#where-synced-skills-load; CHANGELOG 2.1.81. verified.
- Windows paths: "On Windows, `~/.claude` means `%USERPROFILE%\.claude`. To keep the home-directory files somewhere else, set `CLAUDE_CONFIG_DIR`; Claude Code then stores your settings, session history, and plugins there instead." Synced plugins land in `~/.claude/plugins/synced/`, removed ones in `~/.claude/plugins/.trash/`; "If you set `CLAUDE_CONFIG_DIR`, every `~/.claude` path on this page lives under that directory instead." Source: settings.md; claude-directory.md. verified.

### 2. Desktop app, Code tab

- Its own engine copy: "In a local session, the **Code** tab runs its own copy of Claude Code, which has its own version number. The desktop app downloads and updates that copy, so it can differ from the `claude` command in your terminal, and updating one doesn't update the other." `/status` in a local session shows the version. Source: desktop#claude-code-version-in-the-code-tab. verified.
- Shared `~/.claude`: "Desktop and CLI read the same configuration files"; "Settings in `~/.claude.json` and `~/.claude/settings.json` are shared"; "Hooks and skills defined in settings apply to both"; "Local sessions load your personal skills from `~/.claude/skills/`". The Plugins submenu of the **+** button shows "your installed plugins and their skills"; "If your organization manages plugins centrally, those plugins are available in desktop sessions the same way they are in the CLI". Source: desktop#shared-configuration, #use-skills, #install-plugins. verified. That a user-scope `claude plugin install` (which writes `enabledPlugins` into the shared `~/.claude/settings.json` and files under `~/.claude/plugins/`) therefore loads in the Code tab follows from these, but no sentence says it outright. inferred.
- Account plugins do arrive, by the app's own hand: "The desktop app manages some plugins itself, including plugins synced from claude.ai and plugins your organization deploys through the app. If you deploy this key [`disableSideloadFlags`] to a device [...], the desktop app doesn't pass those plugins to the following sessions on that device: Code sessions on the user's machine: they also start without the skills enabled for the user's claude.ai account. Plugins that Claude Code installs from marketplaces in your managed settings still load. [...] Before Claude Desktop v1.37937.0, these sessions failed at startup instead." The claude.com matrix defines "Claude Code: the terminal, the IDE extensions, and the desktop app's Code tab" and says "A plugin you install on your account also appears in Claude Code as a synced plugin at the next session start". Source: settings-reference#disablesideloadflags; platform-support. verified (as docs claims).
- Not the CLI's sync: every description of the `@synced` download names only two places, "Synced plugins load in Cowork sessions and in terminal sessions where you sign in with your claude.ai account"; `syncClaudeAiPlugins` says the download happens "at the start of terminal sessions where you sign in with your claude.ai account and in Cowork sessions"; the desktop page says Claude Code loads account plugins "in terminal sessions where you sign in with the same account". The Code tab is never named there. Source: loading#synced-plugins; settings-reference#syncclaudeaiplugins; desktop#extend-claude-code. verified (by wording and absence).
- Mechanism: `disableSideloadFlags` rejects exactly `--plugin-dir`, `--plugin-url`, `--agents` and `--mcp-config` (and `CLAUDE_CODE_PLUGIN_DIRS`), and the same key stops the app's delivery, so the app hands the account plugins to the session through one of those flags or its SDK equivalent. Synced skills already travel that way: the deny-rule table lists `Skill(anthropic-skills:deploy)` as blocking "That skill when Claude Desktop delivers it to a session as a plugin" and `Skill(deploy:deploy)` as "The plugin form of a synced skill". Consequences if so: the plugin's id in that session is `<name>@inline` rather than `<name>@synced`; it sits at rank 2 and "replaces" a same-named installed marketplace plugin "silently", the reverse of the terminal; and `syncClaudeAiPlugins: false`, documented for the CLI download, may not stop the app's delivery. Source: settings-reference#disablesideloadflags; skills deny-rule table; loading#name-conflicts. inferred.
- Auth: "Claude Desktop and cloud sessions do not call `apiKeyHelper` or read these environment variables: they use OAuth"; `/desktop` "is not available with API key authentication". The token skip list of section 1 therefore cannot apply to the Code tab; its sessions are always account sessions. Source: authentication.md; desktop#coming-from-the-cli. verified.
- `/plugin` has no panel in the Code tab: "Terminal-dialog commands [...] behave differently in the Code tab"; 2.1.290 "Improved the reply to `/plugin` in the desktop app's Code tab: it now says where to install and manage plugins there". Source: desktop#whats-not-available-in-desktop; CHANGELOG 2.1.290. verified.
- Environment: "On Windows, the app inherits user and system environment variables but does not read PowerShell profiles." So a `CLAUDE_CONFIG_DIR` set as a user environment variable reaches the Code tab and one exported only in a PowerShell profile does not; whether the bundled copy then resolves the same directory as the terminal is not stated. Source: desktop#local-sessions. env inheritance verified; config-dir sharing inferred.
- WSL sessions: "A few features aren't available in WSL sessions yet: the integrated terminal, connectors and plugins, [...]"; "Plugins aren't available in WSL sessions." The session's "Claude Code process, its tools, and git all execute inside the distribution". Source: desktop-wsl; desktop#install-plugins. verified. Whether such a session reads the distribution's `~/.claude/skills/` is not stated; the process runs in the distribution, so its `~/.claude` is the distribution's. inferred.
- Cloud sessions started from the Code tab: "The plugin browser is not available in cloud sessions, and plugins you install from the desktop app aren't available for cloud sessions. A cloud session also doesn't install plugins that the repository's `.claude/settings.json` declares". Source: desktop#install-plugins. verified; the rest is section 5.

### 3. Desktop app: Chat and Cowork

- Columns on claude.com: "Chat: conversations in claude.ai on the web, in the Claude desktop app, and in the mobile apps"; "Cowork: Cowork tasks in the desktop app". "Chat and Cowork read plugins from your claude.ai account, and Claude Code reads them from the machine it runs on." Chat loads skills and commands ("Loads as a skill; Claude applies it when it fits") and ignores agents, hooks, local MCP servers, `bin/`, LSP servers, output styles, themes and `settings`; Cowork loads skills, commands (`/plugin-name:command`), agents, hooks and local MCP servers "when the Cowork session runs on your computer". Source: platform-support#compare-component-support-by-app. verified.
- Cowork: "The Cowork tab in the Desktop app sources its skills, plugins, and connectors from this Customize configuration, which syncs through your claude.ai account, not from the CLI's `~/.claude` directory." "Cowork: Claude Code downloads them into the session's own environment when the session starts". Source: desktop#extend-claude-code; loading#synced-plugins. verified. Nothing installed on the PC can hide or duplicate a plugin in Chat or Cowork.
- Enabling a plugin for the account is UI only: "Customize > Plugins in claude.ai or the desktop app"; the three library plugins not enabled on Justin's account (diagram-design, frontend-design, play) are a click there, as ADR-0007 already records. Source: platform-support; ADR-0007. verified.

### 4. IDE extensions

- VS Code: "The extension bundles its own copy of the CLI (command-line interface) for the chat panel"; "The extension's version number is the Claude Code version it bundles"; sign-in is "Sign in and complete authorization in your browser"; "Claude Code settings in `~/.claude/settings.json`: shared between the extension and CLI"; "Plugin management in VS Code uses the same CLI commands under the hood. Plugins and marketplaces you configure in the extension are also available in the CLI, and vice versa." `apiKeyHelper`, `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` "apply to the CLI and the surfaces that wrap it, including the VS Code extension". Source: vs-code.md; authentication.md. verified. The claude.com matrix counts "the IDE extensions" as Claude Code, where account plugins appear as synced plugins (verified). Whether the extension's sessions count as "terminal sessions" for the background sync is not written; given the same engine, the same `~/.claude` and the same `/login` credential, the sync and the rank-5 precedence should behave as in the terminal once the extension is 2.1.273 or later. inferred.
- JetBrains: "The plugin runs the `claude` command in your IDE's integrated terminal and connects to it. It does not bundle its own copy of the CLI". It is the terminal surface; every fact of section 1 applies. Source: jetbrains.md. verified.

### 5. Cloud sessions (this container)

- Claude Code 2.1.296, `CLAUDE_CODE_REMOTE=true`, `claude auth status` prints `"authMethod": "oauth_token"`, `"configDirectory": "/root/.claude"`. `claude plugin list` prints a `Synced from claude.ai:` section with nine plugins (`trident`, `design`, `pstack`, `matt-pocock`, `oneezy`, `searchfit-seo`, `data`, `cowork-plugin-management`, `figma`), each `Status: √ loaded`. `claude plugin list --json` entries: `{ "id": "oneezy@synced", "version": "unknown", "scope": "synced", "enabled": true, "installPath": "/root/.claude/plugins/synced/<org-uuid>_<user-uuid>/oneezy" }`; `version` comes from `.claude-plugin/plugin.json` (the library's packages have none there, so `unknown`; the root `plugin.json` says `0.43.1`), and `design@synced` lives in a folder named by a UUID with `"name": "design"` in its manifest. Source: run here. verified.
- Folder shape: `~/.claude/plugins/synced/<org>_<user>/` holds one folder per plugin, a `<name>.meta.json` (`{"server_plugin_id","marketplace_name":"skills","installation_preference":"available"}`) and `manifest.json` (`{"lastUpdated", "plugins":[{"pluginId","name","description","version":"0007","updatedAt","marketplaceName":"skills","installationPreference":"available"}]}`); `marketplaceName` is the claude.ai label, `version` the account's upload counter. `~/.claude/plugins/` has no `installed_plugins.json`, `known_marketplaces.json` or `cache/`: a fresh cloud session has no CLI-installed plugin. Source: run here. verified.
- Changelog: 2.1.239 "Cloud sessions: plugins synced from claude.ai now show as `name@synced`, work with `claude plugin enable/disable <name>@synced`, and never override a same-named plugin you installed"; 2.1.287 "Fixed SessionStart hooks from synced plugins not running in new cloud sessions"; 2.1.296 "Fixed skills synced from claude.ai never finishing their install [...] when several sessions share a config directory". Source: CHANGELOG. verified.
- What a cloud session does not carry: "Plugins enabled only in your user settings: No"; "Plugins and marketplaces declared in your repo's `.claude/settings.json`: No"; `~/.claude/skills/` from your machine: No, "Cloud sessions automatically load skills you enable on claude.ai". Source: cloud-environments#what-carries-over-from-your-setup. verified. The only way a same-named plugin hides `@synced` here is a setup script that runs `claude plugin marketplace add` and `claude plugin install`; the duplicates the grilling log saw in cloud threads were loose links from the setup script, not plugins. verified (no install record here).
- The cloud credential is an OAuth token, which section 1 lists as a terminal skip condition, yet the plugins arrive: the cloud download is its own path, not the terminal background sync. observation verified, explanation inferred.

## PC checks for the inferred claims

Run on the Windows PC, or through a Remote Control session whose host is the surface under test (a session hosted by the terminal CLI answers A; one hosted by the desktop app answers B; CHANGELOG 2.1.252 names "Remote Control sessions hosted by Claude Desktop or VS Code").

A. Terminal CLI (PowerShell):

```
claude --version                                   # 2.1.273 or later
claude auth status                                 # "authMethod": "claude.ai" (not api_key or a token)
claude plugin list --json                          # yes = entries with "scope": "synced"
Get-ChildItem $env:USERPROFILE\.claude\plugins\synced\*\  # yes = oneezy, matt-pocock, pstack, trident folders
Select-String syncClaudeAiPlugins $env:USERPROFILE\.claude\settings.json   # must print nothing or not "false"
```

Precedence: while `oneezy@oneezy-skills` is still installed, `claude plugin list` shows it `loaded` and `oneezy@synced` not loaded; after `claude plugin uninstall oneezy@oneezy-skills --scope user` a new `claude plugin list` shows `oneezy@synced` `loaded`. That is the hide, confirmed.

B. Desktop app, Code tab, a local session on Windows:

1. `/status`: read the Claude Code row (the bundled version).
2. Type `/oneezy:` in the prompt box: the list offers `oneezy:oneezy-status` and the other eight. Yes = some `oneezy` plugin is loaded in the Code tab.
3. Ask the session to run the `oneezy:oneezy-status` skill and report the absolute path of the SKILL.md it loaded (the Skill tool names the skill's base directory). A path under `...\.claude\plugins\synced\` or a desktop-managed folder = the account copy; under `...\.claude\plugins\cache\oneezy-skills\...` or `...\plugins\marketplaces\...` = the CLI-installed copy hides it there too.
4. Repeat 3 after `claude plugin uninstall oneezy@oneezy-skills --scope user` in a terminal and a new local session; the path must now be the account copy. If step 3 already named the account copy while the CLI copy was installed, the Code tab's order is the reverse of the terminal's (the `--plugin-dir`-class inference holds).
5. Type `/plugin`: the expected reply says where to manage plugins (no panel).
6. Config dir: ask the session to print `$env:CLAUDE_CONFIG_DIR` and `$env:USERPROFILE`; the terminal's `claude auth status` prints `configDirectory`. Same directory = one shared store.

C. VS Code extension: Extensions view shows the Claude Code version (2.1.273 or later); type `/oneezy:` in the panel as in B.2, and B.3 for the path.

D. WSL session in the Code tab (only if Justin uses one): `/oneezy:` offers nothing from any plugin (expected); type `/` to see whether skills from the distribution's `~/.claude/skills/` are listed.

## What tools#149 must keep as a fallback

- Terminal CLI, JetBrains, VS Code, cloud: account plugins arrive; no second form. The one guard the ticket already demands is the fallback: remove the tool-installed plugin and its loose links only after `claude plugin list --json` on that machine shows the same-named `<id>@synced` entry. When it shows no synced entry at all, the sync leaves the harness as it is and reports the likely cause with its fix: Claude Code older than 2.1.273 (`claude update`), a sign-in that predates it (`/login`), `"authMethod"` not `claude.ai` in `claude auth status` (token or API key), `syncClaudeAiPlugins: false` in `~/.claude/settings.json` or `.claude/settings.local.json`, or a plugin not enabled on the account (Customize > Plugins, UI only).
- Desktop app, Code tab, local sessions: the docs say the account plugins arrive, so by default nothing extra. If check B fails (no `oneezy:` skill once the CLI copy is gone), the fallback is the marketplace plugin form skills-sync 0.7.6 installs today (`claude plugin marketplace add oneezy/skills`, `claude plugin install <id>@<marketplace> --scope user`), kept on that machine as a machine fact in the tool's settings (ADR-0012), with the known cost that it hides `@synced` in the terminal: same skills, one name each, one form. Never loose links in `~/.claude/skills/`: the Code tab and the terminal share that directory, so links would list every skill twice in the terminal again, which is the state ADR-0007 removes.
- Desktop app, Code tab, WSL sessions: no plugins of any kind, so the only form that can reach one is loose links inside the distribution's `~/.claude/skills/`, and those duplicate the `@synced` names of the distribution's own terminal `claude`. Out of scope for #149 unless Justin uses WSL sessions in the Code tab; if he does, it is his call which of the two WSL surfaces loses.
- Chat and Cowork: account only; nothing on the PC matters. The three plugins the account does not deliver yet (diagram-design, frontend-design, play) are a manual step at claude.ai and stay in the report as such.
- Cloud: the setup script's skills-sync line must stop creating loose links or installing plugins for Claude Code (ADR-0007: cloud gets the global block only), or `@synced` is duplicated or hidden there again.
