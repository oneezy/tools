# Duplicate-listing probe (skills@1.7.0 against the decided layout)

## Summary

Nothing lists twice: with `skills/oneezy/<name>` beside `plugins/oneezy/skills/<name>` (identical bytes) and both root catalogs present, `npx skills add <lib> --list` and `--list --full-depth` print each own skill once (`Found 4 skills`), because `add` drops same-name duplicates first-seen-wins and `skills/` is walked before the plugin dirs. The defect is one step later: `npx skills update -p -y` in a consumer project discovers with duplicates kept, finds two paths per own skill, prints `Warning: Multiple current paths match these skills from <source>; skipping them rather than deleting or migrating the wrong skill:` and never updates any own skill again (exit 0, counted as success). A side effect of the Claude catalog: `./plugins/<id>` sources make the CLI scan `plugins/<id>/skills`, so third-party copies (`pr` from `plugins/matt-pocock`) are listed and installed as skills of oneezy/skills.
Candidate fixes (a) marketplace `skills` paths, (b) a root `skills-lock.json`, (c) a different plugin skill folder name change nothing. Two fixes work end to end and pass `claude plugin validate` and `codex plugin marketplace add`: (d1) `metadata.internal: true` in the frontmatter of every plugin copy (a build transform; the copies stop being byte-identical), or (d2) put the packages under `dist/` (a name the CLI never walks) and list them in `.claude-plugin/marketplace.json` as bare names under `metadata.pluginRoot: "./dist"`. Codex accepts the catalog with relative sources in every variant and also reads `.claude-plugin/marketplace.json` when `.agents/plugins/marketplace.json` is absent.

### Candidate fixes (each: fresh fixture, `add --list`, `--list --full-depth`, `add file://…git -y`, `update -p -y`; logs under runs/<variant> and runs/git-<variant>)

- (a) Marketplace entry `"skills": ["./skills/oneezy-status", "./skills/oneezy-merge"]` (the only `skills` key the CLI reads): unchanged, 4 listed once, update skips both own skills. The entry's `skills` only adds parent dirs (plugin-manifest.ts L60-70) and `<pluginBase>/skills` is always added (L74); a plugin's own `.claude-plugin/plugin.json` is never opened, only a root one (L104). verified
- (b) Root `skills-lock.json` in the library listing the plugin copies: unchanged. `isInstalledProjectSkill` applies only to paths under the 31 agent dirs (`AGENT_PROJECT_SKILL_DIRS`, src/skills.ts L12-43, L213-225), never `plugins/`. verified
- (c) Plugin skill folder renamed (`plugins/oneezy/skills/status/`): unchanged. Identity is frontmatter `name` (src/skills.ts L127, L276; src/skill-relocation.ts L36), not the folder. verified
- (d1) `metadata:\n  internal: true` inserted after `description` in both plugin copies: `add --list` and `--full-depth` still `Found 4 skills` once each; `update -p -y` prints no warning and `✓ Updated 4 skill(s)` (oneezy-merge and oneezy-status included). Mechanism: `parseSkillMd` returns null for `metadata.internal === true` unless `INSTALL_INTERNAL_SKILLS=1` (src/skills.ts L117-124; README L399-401, L539). `claude plugin validate` on root, `plugins/oneezy` and `plugins/oneezy/skills` passes (version warnings only). Claude Code docs: `metadata` is a documented frontmatter field, "Free-form YAML map … Claude Code doesn't act on its contents, and drops a value that isn't a map", and "Claude Code ignores a field it doesn't recognize without reporting an error" (code.claude.com/docs/en/skills.md, Frontmatter reference). Agent Skills spec: `metadata` optional, "a map from string keys to string values" (agentskills.io/specification), so a boolean `true` is a spec deviation the CLI requires (`=== true`, L121). Codex docs list only `name` and `description` and put extra metadata in `agents/openai.yaml`; tolerance of a `metadata` key is inferred from the spec, not tested in a Codex session. Cost: plugin copies differ from `skills/…` by two lines, so `build` must apply the transform and `build --check` compare after it; `INSTALL_INTERNAL_SKILLS=1` re-exposes the copies. verified (CLI, Claude validate); inferred (Codex)
- (d2) Packages under `dist/<id>`, `.claude-plugin/marketplace.json` with `"metadata": {"pluginRoot": "./dist"}` and bare `"source": "oneezy"` / `"matt-pocock"`, Codex catalog keeps `./dist/<id>`: `add --list` and `--full-depth` `Found 3 skills` (own skills once, `pr` no longer served); `update -p -y` `✓ Updated 3 skill(s)`, no warning. `claude plugin validate .` and `./dist/oneezy` pass (version warnings); `codex plugin marketplace add` accepted, `list --available` shows both with `…\dist\oneezy` paths. Mechanism: `dist` is in `SKIP_DIRS` (src/skills.ts L10), never descended by the container walk (L296) or the full-depth fallback (L149); the bare-name entries fail the `./` check (plugin-manifest.ts L92), so no plugin dir is added. Bare names need Claude Code ≥ 2.1.239 (marketplace-reference L67, L175). Cost: a committed folder named `dist`, and the hiding rests on the CLI ignoring bare names, a side effect rather than a contract. verified
- (d2b) `plugins/` kept, bare names only: plain `--list` 3 (plugin dirs not added), `--full-depth` 4, `update` still warns and skips both. Not a fix. verified
- (d3) `dist/` with `./dist/<id>` string sources: the catalog re-adds `dist/<id>/skills` as search dirs; 4 listed, update skips both. Not a fix; the two halves of (d2) are both required. verified
- (e) Upstream: `resolveSkillLocations` fails closed on `candidates.length > 1` (src/skill-relocation.ts L56-59) before testing whether the locked path is still present (L61). Preferring an exact locked path would end the skip; for GitHub sources the reinstall is already path-targeted (`appendFolderAndRef`, src/update-source.ts L102-108, L49-61). Not in our control; untested. inferred
