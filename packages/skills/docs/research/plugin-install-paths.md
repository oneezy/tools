# Plugin install paths on Claude Code and Codex

## Summary

Both hosts install a plugin from a local marketplace directory with two shell commands, no TTY and no login, and both hosts write their own settings file while doing it: Claude Code puts `extraKnownMarketplaces` (on `marketplace add`) and `enabledPlugins` (on `install`) into `~/.claude/settings.json`; Codex puts `[marketplaces.<name>]` (on `marketplace add`) and `[plugins."<id>"] enabled = true` (on `plugin add`) into `~/.codex/config.toml`. There is no install route on either host that leaves the settings file alone, so #74's "if a host's install path requires a settings edit, stop" clause fires on both hosts unless the rule is read as "the tool never edits settings itself". Proof of load without a session: `claude plugin list --json` (`enabled: true`) plus `claude plugin details <plugin>` (lists the skill), and `codex plugin list --json` (`installed: true, enabled: true`) plus `codex debug prompt-input` (lists `<plugin>:<skill>`). Claude Code loads a local-directory marketplace plugin in place (a cache copy is written but not read), Codex loads its cache copy keyed by version. Rollback: Claude's `marketplace remove` cascades to its plugins; Codex's does not, so on Codex the tool must `plugin remove` before `marketplace remove` or the cached skill keeps reaching the model. A copied skill folder carrying `agents/openai.yaml` loads on both hosts with no warning. Not settled: whether `claude -p "/<plugin>:<skill>"` runs from an installed plugin (needs login on the temp config dir; the credential copy was refused by the permission system).

## Facts

Probe layout (mirrors #72's build output): `mkt/.claude-plugin/marketplace.json`, `mkt/.agents/plugins/marketplace.json`, `mkt/plugins/probe-oneezy/{plugin.json, .claude-plugin/plugin.json, .codex-plugin/plugin.json, skills/probe-hello/SKILL.md, skills/probe-hello/agents/openai.yaml}`; `.claude-plugin/plugin.json` has no `version`, the other two carry `0.1.0+probe`. `claude plugin validate ./mkt` and `validate ./mkt/plugins/probe-oneezy`: exit 0, one warning (no version). All Claude probes ran with `CLAUDE_CONFIG_DIR`, `HOME`, `USERPROFILE` at temp dirs, stdin `/dev/null`, no credentials; all Codex probes with `CODEX_HOME`, `HOME`, `USERPROFILE` at temp dirs, `codex login status` = "Not logged in". verified.

### Claude Code 2.1.286

1. `claude plugin marketplace add ./mkt` -> exit 0, `Successfully added marketplace: probe-mkt (declared in user settings)`. Host writes: `settings.json` -> `extraKnownMarketplaces.probe-mkt = {source: {source: "directory", path: <abs>}}`; `plugins/known_marketplaces.json` -> `{probe-mkt: {source, installLocation: <the path given>, lastUpdated}}`; `.claude.json` (firstStartTime, machineID, userID) and `backups/.claude.json.backup.*`. Repeat add: exit 0, `Marketplace 'probe-mkt' already on disk — declared in user settings`. [probes/claude-steps-1-3.log; cli-reference#plugin-marketplace-add; loading#check-which-stage-a-plugin-reached] verified
2. `claude plugin install probe-oneezy@probe-mkt --scope user --json` -> exit 0, last line `{"command":"install","outcome":"ok","plugin":"probe-oneezy@probe-mkt","pluginId":"probe-oneezy@probe-mkt","scope":"user","message":"Successfully installed plugin: ..."}`. Host writes: `settings.json` -> `enabledPlugins["probe-oneezy@probe-mkt"] = true`; `plugins/installed_plugins.json` -> `{version: 2, plugins: {"probe-oneezy@probe-mkt": [{scope: "user", installPath: <cache>, version: "unknown", installedAt, lastUpdated}]}}`; a full copy of the plugin at `plugins/cache/probe-mkt/probe-oneezy/unknown/` (plain directory, not a reparse point, byte-identical to the source). Repeat install: exit 0, `already installed (scope: user) — it loads in place from <mkt>/plugins/probe-oneezy, so edits there take effect at the next session start or /reload-plugins`. [probes/claude-steps-1-3.log] verified
3. In place, not cache: editing the cache copy's `.claude-plugin/plugin.json` description and adding a cache-only `skills/cache-only/SKILL.md` changed nothing in `claude plugin details` (still `Skills (1) probe-hello`, original description). loading.md: "Relative-path plugins in a marketplace you added from a local directory: the plugin loads in place". A rebuilt `plugins/<id>` therefore reaches the next session without reinstall. Version is `unknown` because mkt/ is not a git repo; loading.md says a relative-path plugin inside a git-hosted or git-cloned marketplace gets the commit SHA of its directory. [probes/claude-inplace-reprobe.log R3/R4; loading#in-place-and-copied-plugins, #how-claude-code-computes-the-version] verified (details/in-place); inferred (git-clone version)
4. Proof of load without a session or login: `claude plugin list` -> `Installed plugins: probe-oneezy@probe-mkt / Version: unknown / Scope: user / Status: ✔ enabled`; `--json` -> `[{id, version, scope, enabled: true, installPath, installedAt, lastUpdated, projectEnabled: false}]` with no `errors`/`notes` keys (they appear only on a failed or warned load). `claude plugin details probe-oneezy` (or `probe-oneezy@probe-mkt`) -> `Component inventory / Skills (1)  probe-hello / Agents (0) / Hooks (0) ...` plus `Projected token cost`, exit 0; an unloaded name exits 1 with `Plugin "<name>" not found`. [probes/claude-steps-1-3.log; cli-reference#plugin-list, #plugin-details] verified
5. `claude -p "/probe-oneezy:probe-hello"` from the installed plugin: not run. `claude -p` on the temp config dir answers `Not logged in · Please run /login`, exit 1; copying the real `.credentials.json` into the temp dir was denied by the harness permission classifier, and so was a follow-up docs lookup for an alternative. install.md states "`claude -p` ... Plugins you already installed do load", and the prior note verified `/<plugin>:<skill>` runs under `-p` for a `--plugin-dir` plugin. [probes/claude-p attempt; install#other-places-you-run-claude-code; claude-code-plugins.md fact 4] unknown (installed form); inferred from docs that it works
6. Rollback: `claude plugin uninstall probe-oneezy@probe-mkt --json` -> exit 0, `{"outcome":"ok","keptData":false,...}`; `settings.json` keeps `"enabledPlugins": {}` (key removed, object left), `installed_plugins.json` -> `plugins: {}`, cache dir stays with an `.orphaned_at` marker. Second uninstall: exit 1, `failureCode: "not_installed"`. `claude plugin marketplace remove probe-mkt` -> exit 0, cascades: `Also uninstalled 1 plugin from this marketplace: probe-oneezy@probe-mkt`; leaves `settings.json` as `{"enabledPlugins": {}, "extraKnownMarketplaces": {}}` and `known_marketplaces.json` as `{}`. Second remove: exit 1, `Marketplace 'probe-mkt' not found`. [probes/claude-steps-4-rollback.log; cli-reference#plugin-marketplace-remove] verified
7. Error shape: `install nosuch@probe-mkt --json` and `install probe-oneezy@nomkt --json` both exit 1 with `failureCode: "not_found"` and `Plugin "<x>" not found in marketplace "<m>". Your local copy may be out of date — try claude plugin marketplace update <m>.`; a missing marketplace is not distinguished from a missing plugin. [probes/claude-inplace-reprobe.log R6] verified
8. Scopes: `--scope user` (default) writes `~/.claude/settings.json`; `project` writes the project's `.claude/settings.json`; `local` writes `.claude/settings.local.json`; `marketplace add --scope` declares the marketplace in the same files. Only user scope reaches every project. Not probed. [install#choose-an-install-scope; cli-reference] verified (docs)
9. No TTY needed: every command above ran with stdin at `/dev/null` and exited 0. `-y` is required only for `command`-source or `headersHelper` installs, and is ignored when run from inside a Claude Code session. [probes; cli-reference#plugin-install] verified

### Codex CLI 0.156.1

10. `codex plugin marketplace add ./mkt --json` -> exit 0, `{"marketplaceName":"probe-mkt","installedRoot":"<abs mkt>","alreadyAdded":false}`. Host writes `$CODEX_HOME/config.toml` -> `[marketplaces.probe-mkt] source_type = "local" source = '\\?\C:\...\mkt'` (Windows verbatim-path prefix). Nothing under `.tmp/` for a local source. The name is read from `mkt/.agents/plugins/marketplace.json` (the human `plugin list` prints that path). [probes/codex-steps-1-3.log; help/codex-help.txt] verified
11. `codex plugin add probe-oneezy@probe-mkt --json` -> exit 0, `{"pluginId":"probe-oneezy@probe-mkt","name","marketplaceName","version":"0.1.0+probe","installedPath":"<CODEX_HOME>/plugins/cache/probe-mkt/probe-oneezy/0.1.0+probe","authPolicy":"ON_USE"}`. Host writes `[plugins."probe-oneezy@probe-mkt"] enabled = true` into config.toml and copies the plugin to `plugins/cache/<mkt>/<plugin>/<version>/`. Repeat add: exit 0, identical JSON, no "already" flag. [probes/codex-steps-1-3.log] verified
12. Codex loads the cache copy, not the source: `codex debug prompt-input "hello"` lists `probe-oneezy:probe-hello: <description> (file: r2/probe-oneezy/0.1.0+probe/skills/probe-hello/SKILL.md)` with `r2 = <CODEX_HOME>/plugins/cache/probe-mkt`. The cache path is keyed by the manifest `version`, so a rebuilt plugin reaches Codex only through a new `plugin add` (and, with an unchanged version string, possibly not at all; see open questions). [probes/codex-steps-1-3.log step 3c] verified (cache path); unknown (same-version refresh)
13. Proof of load without a session or login: `codex plugin list --json` -> `{installed: [{pluginId, name, marketplaceName, version, installed: true, enabled: true, source: {source: "local", path}, marketplaceSource, installPolicy: "AVAILABLE", authPolicy: "ON_USE"}], available: [...]}`; human `codex plugin list` -> table row `probe-oneezy@probe-mkt  installed, enabled  0.1.0+probe  <source path>`. Skill-level proof is `codex debug prompt-input` (fact 12), which ran logged out. There is no `codex plugin details`. [probes/codex-steps-1-3.log; help/codex-help.txt] verified
14. Rollback: `codex plugin remove probe-oneezy@probe-mkt --json` -> exit 0, `{pluginId, name, marketplaceName}`; removes the `[plugins]` entry and the cache version dir (an empty `cache/probe-mkt/` dir remains). Second remove: exit 0, same JSON (idempotent). `codex plugin marketplace remove probe-mkt --json` -> exit 0, `{"marketplaceName":"probe-mkt","installedRoot":null}`; removes only `[marketplaces.probe-mkt]` and does NOT cascade: the `[plugins."..."] enabled = true` line and the cache dir stay, `codex plugin list --json` then reports `installed: []`, yet `codex debug prompt-input` still lists `probe-oneezy:probe-hello` from the cache, and re-adding the marketplace shows the plugin installed and enabled again without a `plugin add`. Second marketplace remove: exit 1, `Error: marketplace \`probe-mkt\` is not configured or installed`. [probes/codex-steps-4-rollback.log; probes/codex-orphan.log] verified
15. Error shape: `codex plugin add probe-oneezy@probe-mkt` with no such marketplace -> exit 1, `Error: plugin \`probe-oneezy\` was not found in marketplace \`probe-mkt\`` (plain text even with `--json`). [probes/codex-steps-4-rollback.log 4c] verified
16. No login, no TTY: every Codex command above ran with stdin `/dev/null` in a CODEX_HOME that has no `auth.json`; `plugin list` and `plugin add` wrote nothing to stderr. [probes/codex-steps-4-rollback.log 3d-3f] verified

19. Where the HOST writes a settings file, stated plainly: Claude Code `marketplace add` -> `~/.claude/settings.json` (`extraKnownMarketplaces`); `install` -> `~/.claude/settings.json` (`enabledPlugins`); `uninstall`/`marketplace remove` edit the same keys. Codex `marketplace add` -> `~/.codex/config.toml` (`[marketplaces.<name>]`); `plugin add` -> `~/.codex/config.toml` (`[plugins."<id>"]`); `remove`s edit the same tables. Neither host offers an install that leaves its settings file untouched; the only no-settings load is Claude's session-only `--plugin-dir`/`CLAUDE_CODE_PLUGIN_DIRS`, which is not an install and is not listed by a later `claude plugin list`. [facts 1, 2, 6, 10, 11, 14; cli-reference#flags-that-load-a-plugin-for-one-session] verified

## Open questions

- Does `claude -p "/probe-oneezy:probe-hello"` run from a marketplace-installed plugin (not `--plugin-dir`)? Docs say installed plugins load under `-p`; not verified here (fact 5).
- Codex: when the built plugin's files change but the manifest `version` does not, does a repeat `codex plugin add` refresh the cache copy? The second add returned the same path; content refresh untested. #72's `0.<commit count>.0+<sha12>` changes per commit, which sidesteps it only if the library is committed before `sync`.
- Claude Code version string when the marketplace is the library's git clone (expected: commit SHA of the plugin directory per loading.md); the probe marketplace was not a git repo, so it read `unknown`.
- Does Claude Code's background marketplace check ever rewrite `settings.json` for a `directory` marketplace? Docs say auto-update is off by default for local marketplaces; not observed either way.
- Does `codex plugin marketplace add` of a git source (`oneezy/skills`) behave the same for `[plugins]` entries? Only the local-directory form was probed.

## Blockers

- Probe (2b), `claude -p` invoking the installed plugin's skill, could not run: the temp config dir has no login, and the harness permission classifier refused copying the real credentials into it (and a follow-up docs read for an alternative route). Justin can settle it himself in one command on a logged-in config dir: `claude plugin marketplace add <lib> && claude plugin install <id>@<mkt> && MSYS_NO_PATHCONV=1 claude -p "/<id>:<skill>" --max-turns 2`, then uninstall.

## Raw notes

- Help texts: help/claude-help.txt, help/codex-help.txt. Codex has no `details`; `codex plugin list --json` gives `{installed, available}` as one object, unlike Claude's array (Claude's `--json --available` also returns an object).
- Claude `plugin list --json` field set observed on a healthy install: `enabled, id, installPath, installedAt, lastUpdated, projectEnabled, scope, version`.
- Claude leaves `"enabledPlugins": {}` and `"extraKnownMarketplaces": {}` behind after full rollback; a settings-diff check in #74 should treat empty objects as "unchanged".
- Codex `config.toml` stores the local marketplace source as a `\\?\` verbatim path; tests that compare config text must expect that prefix on Windows.
- Codex writes `installation_id`, `.sandbox_migration` and the `.system` skills into CODEX_HOME on the first `codex debug prompt-input`; `plugin` subcommands alone wrote only `config.toml` and the cache.
- `claude -p` on the temp config dir wrote a `projects/<cwd>/<uuid>.jsonl` transcript even though it only printed "Not logged in".
- Git Bash rewrites a leading `/word` argument; `MSYS_NO_PATHCONV=1` is needed for any `-p "/..."` test.
