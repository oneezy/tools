# What skill layout do Claude Code and Codex each expect?

Ticket: oneezy/tools#4 (part of map #1). Date: 2026-09-21.
Versions inspected: Claude Code 2.1.278, codex-cli 0.155.1, Windows 11.

## Question

From the official docs and source of each harness, record exactly what Claude Code and Codex expect for a skill: config folder per user and per project, skill folder name, `SKILL.md` frontmatter fields, supporting files, plugin format if any, how a skill is discovered and invoked, and whether symlinked folders are followed. Include the Agent Skills spec itself as the canonical base format. Produce a comparison table and list every divergence a converter would have to handle.

## Summary

1. Both harnesses accept the Agent Skills base unit unchanged: `<name>/SKILL.md` with `name` + `description` frontmatter and optional `scripts/`, `references/`, `assets/`. A spec-conformant skill loads in both without edits.
2. The roots differ: Claude Code reads `~/.claude/skills` and `.claude/skills` (cwd up to repo root) and never scans `.agents/skills`; Codex reads `.agents/skills` (cwd up to repo root), `~/.agents/skills`, the deprecated `~/.codex/skills`, project `.codex/skills`, `/etc/codex/skills`, and its own `~/.codex/skills/.system`.
3. The command name comes from the directory in Claude Code (frontmatter `name` is only a label outside plugins) but from the frontmatter `name` in Codex (directory is the fallback), so a converter must keep the two identical, which is also the spec rule.
4. Harness-specific behaviour lives in different places: Claude Code keeps everything in `SKILL.md` frontmatter (`disable-model-invocation`, `allowed-tools`, `context: fork`, `$ARGUMENTS`, `` !`cmd` `` injection) while Codex reads only `name`, `description`, `metadata.short-description` from frontmatter and puts UI and policy in a sidecar `agents/openai.yaml` (`interface.*`, `policy.allow_implicit_invocation`, `dependencies.tools`).
5. Both follow directory symlinks at the skill-folder level (Codex ignores symlinked `SKILL.md` files and symlinks in its System scope; Claude plugin caches drop symlinks that leave the plugin or marketplace). Plugins and marketplaces are separate formats (`.claude-plugin/plugin.json` + `marketplace.json` vs `.codex-plugin/plugin.json` or portable root `plugin.json` + `.agents/plugins/marketplace.json`); both bundle skills under `skills/<name>/SKILL.md` and expose them as `plugin:skill`.

## Divergences a converter must handle

1. Roots: Claude Code does not scan `.agents/skills` (project or user). A skill kept in `.agents/skills` must be copied or symlinked into `.claude/skills` and `~/.claude/skills` for Claude Code; Codex reads `.agents/skills` natively and also `~/.codex/skills` (deprecated) and project `.codex/skills`. Do not write the same skill to two Codex roots: Codex shows both and `$name` becomes ambiguous.
2. Command-name source: directory name in Claude Code, frontmatter `name` in Codex. Keep them identical (spec rule); renaming only one silently forks the command name across harnesses.
3. Required fields: Codex drops a skill with an empty or missing `description`; Claude Code tolerates a `SKILL.md` with no frontmatter at all. The converter must guarantee a non-empty `description`. Codex collapses it to one line, so multi-line block descriptions flatten.
4. Description budget: spec 1,024 chars; Claude Code truncates `description` + `when_to_use` at 1,536; Codex trims the whole catalog to 2% of context. `when_to_use` is Claude-only, so anything that must trigger in Codex belongs in `description`, trigger words first.
5. Model-invocation gating lives in different files with different semantics: Claude `disable-model-invocation: true` (frontmatter; description withheld from the model) maps to Codex `agents/openai.yaml` `policy.allow_implicit_invocation: false` (skill left out of the catalog but still `$`-invocable). The repo already pairs these for 23 skills.
6. `user-invocable: false` (Claude, hide from the `/` menu, model-only) has no Codex counterpart; `$` mentions are always allowed.
7. Claude-only frontmatter (`argument-hint`, `arguments`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context`, `agent`, `background`, `paths`, `shell`, `hooks`) is ignored by Codex without error, but its behaviour (forked subagent, pre-approved tools, path-scoped activation, effort) is lost. A converter can pass the fields through; it cannot reproduce them.
8. Argument substitution: `$ARGUMENTS`, `$0..$N`, `$issue`, `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}` expand only in Claude Code. In Codex they are literal text, and because `$` is Codex's mention sigil (name chars `A-Za-z0-9_-:`), a token like `$issue` could be read as a skill mention. Write argument handling in prose for Codex.
9. Dynamic context injection (`` !`git diff` `` and `` ```! `` fences) is Claude-only and disabled in synced skills; Codex shows the text verbatim.
10. Display metadata: Codex wants `agents/openai.yaml` `interface.display_name` and a 25-64 char `short_description` (plus optional icons under `assets/`); Claude Code has no equivalent beyond `name` as label. Generate the sidecar from `name`/`description` (Codex ships `skill-creator/scripts/generate_openai_yaml.py`).
11. `metadata`: spec is a string-to-string map; Claude accepts free-form YAML; Codex reads only `metadata.short-description`. Nested objects (the repo's `pr` skill has `metadata.credits.{skill,author}`) violate the spec but break neither harness.
12. Symlinks on Windows: both follow directory symlinks, but creating one needs Developer Mode or elevation, Codex ignores a symlinked `SKILL.md` file (link the directory, not the file), Codex ignores symlinks in System scope, and Claude Code's plugin cache drops symlinks that resolve outside the plugin or marketplace. Git with `core.symlinks=true` records them as mode `120000` entries; this repo's `.claude/skills` is committed as plain copies (mode `100644`), so a sync that creates symlinks on disk diverges from what the repo ships.
13. Nesting: Codex scans recursively to depth 6, so a `SKILL.md` inside a skill's `references/` or `assets/` becomes a second skill; Claude Code expects exactly `<root>/<skill>/SKILL.md`. Never nest `SKILL.md` files.
14. Hidden directories: Codex prunes dot-directories inside a root (a skill folder named `.foo` is invisible); Claude Code only reserves `synced`.
15. Disable mechanisms differ: Claude `skillOverrides: {"name": "off"}` and permission rules `Skill(name)` key on the skill name; Codex `[[skills.config]] path = "<absolute>/SKILL.md"` keys on the absolute path. Moving or re-linking a Codex skill silently re-enables it.
16. Plugin manifest and marketplace formats are not interchangeable: `.claude-plugin/plugin.json` (only `name` required) vs `.codex-plugin/plugin.json` or portable root `plugin.json` (Codex marketplace validation demands `version`, `description`, `author.name`, `interface.*`; legacy manifest rejects `hooks`); `.claude-plugin/marketplace.json` (`owner` required, seven source types) vs `.agents/plugins/marketplace.json` (`policy.installation`, `policy.authentication`, `category` per entry, four source types). Codex does read a legacy `.claude-plugin/marketplace.json`, Claude Code does not read Codex's.
17. Plugin skill naming: both use `plugin:skill`, but Claude Code also exposes the bare `/skill` when unclaimed and lets a plugin skill's frontmatter `name` override the last segment; Codex namespaces from the nearest `plugin.json` above the skill path.
18. Collision policy: Claude Code resolves by precedence (enterprise > personal > project, local over bundled); Codex keeps duplicates and only dedupes by path. A converter that installs to both `~/.claude/skills` and `.claude/skills` gets one winner in Claude Code, but the same pair in `~/.agents/skills` and `.agents/skills` shows twice in Codex.
19. Legacy formats to accept on input: Claude `.claude/commands/<name>.md` (flat file, same frontmatter minus `name` and `paths`, subdir path becomes `a:b`) and Codex `~/.codex/skills`; neither is a target format.
20. Frontmatter robustness: Codex repairs unquoted scalars containing colons; Claude Code's behaviour is undocumented. Always quote a `description` that contains `:`.
