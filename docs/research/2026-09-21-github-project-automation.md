# How much of a GitHub Project can be set up by automation?

Research for oneezy/tools ticket [#5](https://github.com/oneezy/tools/issues/5), part of map [#1](https://github.com/oneezy/tools/issues/1). Observed 2026-09-21 (UTC). Sources: GitHub Docs, the live GraphQL schema (introspected read-only with `gh api graphql`), the REST OpenAPI description (`github/rest-api-description`, `api.github.com.json` v1.1.4, downloaded today), `gh` 2.96.0 `--help` output, GitHub changelog entries, and read-only queries against the user-owned projects `users/layerdbiz/projects/1` ("Trident Cubed") and `users/oneezy/projects/2` ("Work"). Starting material: the four unmerged `research/*` branches on `layerdbiz/tridentcubed` and its `scripts/github-project-sprint-board.sh` wizard, cited below and not merged. Nothing was created, mutated or deleted. Each claim is marked **stable fact** (documented by GitHub or in the live schema), **observed** (seen in a read-only call today), or **unverified** (inferred, or testable only with a write).

## Question

The goal is zero-touch: one command creates a project, its fields, its views (Sprint board, Backlog table, Roadmap), Status options (Todo, Next Up, In Progress, Review, Done), and turns on the built-in workflows, for a repo under either `oneezy` or `layerdbiz`. Which of those steps can be automated, which are browser-only, what token and scope each needs, and how can a shared automation serve both accounts?

## Summary

1. Everything structural is scriptable with one classic PAT carrying the `project` scope, run as the account that will own the project: create the project, add Priority/Estimate/Iteration fields, rewrite the Status options, create the Sprint board (columns by Status), Backlog table and Roadmap, delete the default "View 1", link the repo, and import existing issues. Views need the REST create-view endpoint (2026-01) for column/group/sort; GraphQL grew `createProjectV2View`/`updateProjectV2View` on 2026-07-28 but they only take name, layout, filter and visible fields.
2. The built-in workflows are the browser-only remainder. The API exposes only `name`, `number`, `enabled` per workflow and one mutation, `deleteProjectV2Workflow`. "Auto-add to project" with a repo filter must be clicked on, and "Auto-close issue", which is **on** at creation (observed on two fresh projects), must be clicked off. "Item closed -> Done", "Pull request merged -> Done", "Item added -> Todo", "Pull request linked -> In progress" and "Auto-add sub-issues" are already on when a project is created, so zero-touch gets them for free.
3. Token: classic PAT with `project` (add `repo` to link or read private repos). `GITHUB_TOKEN` cannot reach Projects at all; fine-grained PATs and GitHub Apps cannot reach user-owned projects (documented gap; the REST create-view endpoint for user projects is flagged `enabledForGitHubApps: false` in the OpenAPI file).
4. Cross-account: a user project can only be created, copied to, and linked to repos under the same user, so one script serves both accounts only if it is parameterised by owner and runs with that owner's PAT (`gh auth switch` locally, or one repo secret per account in Actions). One public reusable workflow can be called from any repo of either account; a private host cannot cross accounts.
5. Events: `issues` (`assigned`, `unassigned`, `closed`, `reopened`, `labeled`, ...) and `pull_request` `closed` with `merged == true` are Actions triggers; dependency (`issue_dependencies`) and sub-issue (`sub_issues`) changes are webhooks only, and project-item changes (`projects_v2_item`) are organization webhooks only, so a user-owned board's own moves cannot trigger anything.

Token facts behind the last column:

- `gh project`: "The minimum required scope for the token is: `project`" (`gh project --help`; `gh auth refresh -s project` adds it). `oneezy`'s current `gh` token carries `gist, project, read:org, repo, workflow` (observed via `gh auth status`).
- Classic scopes: `project` "Grants read/write access to user and organization projects"; `read:project` read-only; `repo` "also grants the ability to manage projects owned by users" ([Scopes for OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)).
- `GITHUB_TOKEN`: "`GITHUB_TOKEN` is scoped to the repository level and cannot access projects" ([Automating Projects using Actions](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions)); the same page recommends "a personal access token (recommended for user projects)" created "with the `project` and `repo` scopes".
- Fine-grained PAT: the documented limitations list still includes "Using fine-grained personal access token to access Projects owned by a user account" ([Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#fine-grained-personal-access-tokens-limitations)); the fine-grained permission reference has only "Organization permissions for Projects" and no user-level Projects permission (stable, checked today).
- GitHub App: same permission model (organization Projects only); the user-owned create-view endpoint is `enabledForGitHubApps: false` in the OpenAPI file, while the user-owned items and fields endpoints are `true` (observed). GraphQL writes to a user project with an installation token remain unverified, as tridentcubed's token research already concluded.

## Events

What an automation can react to once the project exists (all stable facts unless marked):

| Change | GitHub Actions trigger | Webhook | Notes |
| --- | --- | --- | --- |
| Issue assigned / unassigned | `issues: types: [assigned, unassigned]`; `github.event.assignee` is the single user | `issues` (`assigned`, `unassigned`), available to repository, organization, app webhooks | Built-in workflows have no assignment trigger; "assigned -> In Progress" is Actions work with the PAT (`updateProjectV2ItemFieldValue`) |
| Issue closed / reopened / labeled | `issues: [closed, reopened, labeled, unlabeled]` | `issues` | Built-in "Item closed -> Done" already covers the Status move for free |
| PR merged | `pull_request: [closed]` with `if: github.event.pull_request.merged == true` (no `merged` type exists) | `pull_request` `closed` with `merged: true` | Built-in "Pull request merged -> Done" covers the PR item; linked issues need the workflow (closing keywords only work for PRs into the default branch) |
| PR opened / ready for review | `pull_request: [opened, ready_for_review, converted_to_draft]` | `pull_request` | Built-in "Pull request linked to issue -> In progress" covers the linked issue |
| Dependency (blocked-by / blocking) added or removed | **None.** `issue_dependencies` is not in the Actions event list | `issue_dependencies` (`blocked_by_added`, `blocked_by_removed`, `blocking_added`, `blocking_removed`), repository/organization/app | React via `schedule`, recompute on any `issues` event, or a webhook receiver that calls `repository_dispatch` |
| Sub-issue / parent added or removed | **None.** | `sub_issues` (`parent_issue_added`, `parent_issue_removed`, `sub_issue_added`, `sub_issue_removed`) | Built-in "Auto-add sub-issues" adds the child to the board; nothing else fires |
| Project item created / edited / moved (Status changed on the board) | **None.** | `projects_v2_item` (`created`, `edited`, `archived`, ...) is **organization** webhooks only; `projects_v2` and `projects_v2_status_update` likewise | For a user-owned project, board moves are invisible to automation except by polling `ProjectV2.items` or the issue timeline (`project_v2_item_status_changed`) |
| Issue typed / untyped | `issues: [typed, untyped]` | `issues` | Issue types are organization-only; not available to these accounts |

## Recommendation

1. Build the bootstrap as a `gh`-driven script (bash, matching the wizard's library) taking `--owner`, `--repo`, `--title`, run with the owner account's classic PAT (`project` + `repo`). Order: `gh project create` -> `createProjectV2Field` for Priority, Estimate, Iteration -> `updateProjectV2Field` to set Status to Todo / Next Up / In Progress / Review / Done (carrying existing option ids) -> REST create-view for Sprint (board, `vertical_group_by` Status), Backlog (table, `is:open -status:Done`, sorted by Priority) and Roadmap -> `deleteProjectV2View` on "View 1" -> `gh project link` -> import issues -> verify the six default workflows are `enabled` -> open `/workflows` and wait until `Auto-add to project` reports `enabled: true` and `Auto-close issue` reports `false`. Everything but the last step is unattended; the last step is two clicks and is verifiable from the API, so the script can refuse to finish until it sees them.
2. Do not build the zero-touch path on `gh project copy` of a golden project: it cannot cross accounts, does not carry auto-add, and still leaves Auto-close to switch off, so it saves nothing over the script while adding a hand-maintained source project per account.
3. Hold one classic PAT per account (`oneezy`, `layerdbiz`), each with `project` and `repo`, an expiry, and a rotation reminder. Locally, `gh auth switch`; in Actions, a repository secret per caller. Do not plan on fine-grained PATs, GitHub Apps or `GITHUB_TOKEN` for user-owned projects until GitHub closes the documented gap.
4. Before writing the script, run three cheap experiments on a throwaway project (they need writes, so they were out of scope here): (a) does the REST create-view path accept a login in `{user_id}` or only the numeric id; (b) does `deleteProjectV2Workflow` on "Auto-close issue" switch it off, which would make step 6 fully automatic; (c) does a GraphQL `createProjectV2View(BOARD_LAYOUT)` default its columns to Status, which would remove the REST dependency. Also confirm that renaming Status options does not detach the default "-> Done"/"-> Todo"/"-> In progress" workflows.
5. Event-driven board sync (assigned -> In Progress, unblocked -> Next Up) is a separate build on the public reusable-workflow host tridentcubed's research already recommends; the bootstrap script should not try to fold it in.
